# USBプロトコル解析メモ

## 対象

`mnservice.exe`（ネイティブサービス）が XHEAD-USB 実機と行う生のUSB通信。
gRPC (`docs/protocol/`) はあくまで **PC内の GUI⇔サービス間** の通信であり、実機との
通信プロトコルとは別レイヤ。ここが未解析の最後のブラックボックス。

## 現状の環境

- 実機は `VID_17A7&PID_0008` として認識。
- **確認済み(2026-07-24)**: ドライバクラスが **libusbk devices** (provider libusbK, v3.1.0.0,
  `oem122.inf`) になっており、公式アプリはこの状態で実機接続に失敗する
  （`XHEAD Studio: XHEAD-USBの接続に失敗しました。` ダイアログ）。
  - デバイスの `CompatibleID` に `USB\MS_COMP_WINUSB` が含まれており、これはデバイス
    ファームウェア自身がMS OS Descriptor経由のWinUSB自動バインドに対応していることを示す。
    つまり本来のドライバは **WinUSB**（Microsoft純正・署名済み）であり、専用ベンダードライバ
    ではないと推定される。
  - `C:\sdrsharp-x86\zadig.exe` がこのマシンに存在しており、RTL-SDR用ドライバ導入時に
    誤ってXHEAD-USBの方のドライバもlibusbKへ差し替えてしまったと推測される。
  - **対処法**: デバイスマネージャーでドライバを削除→USB抜き差しで再列挙させ、WinUSBへの
    自動バインドを待つ。または Zadig で明示的に XHEAD-USB → WinUSB を選んで
    "Replace Driver" する（RTL-SDR側のデバイスと誤選択しないよう要注意）。
  - `mnservice.exe` は gRPC (localhost:50051) 自体は正常に待受けており、この問題は
    純粋に `mnservice.exe` ⇔ 実機のUSBオープンの失敗（WinUSB API呼び出し失敗）と考えられる。
    自作ツール (`tools/custom_sender`) で `connectService` した際も
    `Status=StatusOffline` が返り、実機非接続状態と整合する。
- Wireshark + USBPcap はインストール済み (`C:\Program Files\Wireshark`, `C:\Program Files\USBPcap`)。

## 結果 (2026-07-25): 実データのキャプチャに成功、基本フレーミングを解読

### 経緯: 最初の2回は謎の空振り、3回目（別ハブへの挿し替え後）で成功

`tshark`（管理者権限で実行、`IsInRole(Administrator)`で確認済み）で`\\.\USBPcap3`
（実機が列挙されているルートハブ）を対象に、`mnservice.exe`をキャプチャ開始後に再起動→
自作ツールでフル送出パイプラインを実行、という手順を試したが、**最初の2回（同一USBポート/
同一デバイスインスタンスID `B103140916AB` のまま）は実データ転送が一切キャプチャできず**、
`GET DESCRIPTOR`/`SET CONFIGURATION`の6パケットのみだった。これはキャプチャ開始時に
接続済みの全USBデバイスに対して一律に発生する合成/注入パケットで、実際のI/Oではないと
判明した（アドレス1〜19の全デバイスで全く同じ6パケットパターンを確認）。ルートハブ選択
ミス・Isochronous起因・管理者権限不足はいずれも根拠を確認して否定した。

その後、**ユーザーが実機のケーブルを物理的に別のUSBハブへ挿し替えた**ところ（同じ
`USBPcap3`＝同じホストコントローラ配下だが、新しいポート番号・新しいUSBアドレス`3.48`で
再列挙）、**同じ手順で今度は実データが正常にキャプチャできた**（コントロール転送1242
パケット、バルク転送359パケット）。原因はデバイス移動そのものというより、**新規の完全な
USB列挙**が発生したことだと考えられる（同一デバイスインスタンスのまま`mnservice.exe`だけを
再起動しても、WinUSBパイプハンドルが何らかの理由でUSBPcapから見えない状態になっていた
可能性がある）。同じ症状が再発した場合は、デバイスを一度物理的に抜き差しして完全な
再列挙を発生させるのが有効な回避策と考えられる。

### 判明したフレーミング

**バルク転送 (Endpoint 0x81 IN / 0x01 OUT, `bmAttributes=0x02`=BULK)**:

- 転送サイズは一貫して **24064バイト** = `mnservice.exe`の自ログ
  `mslicebuffer.cc:50] slice buffer size : [24064:224:5390336]`の先頭値と完全一致。
  128 × 188 = 24064 で、MPEG-TSパケット（188バイト）128個分ぴったりに相当する。
- ペイロードをバイト単位で調べたところ、**オフセット3, 191, 379, 567, ...
  （3 + 188×n、stride=188で完全に規則的）に`0x47`（MPEG-TS同期バイト）が並んでいる**ことを
  確認した。つまり中身は生のMPEG-TSパケット列そのもの。
- ただし各転送の先頭3バイトだけは同期バイトの前にある「ヘッダ」で、複数の転送を比較すると
  値が転送ごとに変化する（例: `10 00 40`, `14 12 40`, `16 12 40`, `1c 12 40`, `11 01 41`...）。
  単純な単調増加カウンタではなさそうで、意味は未解読（シーケンス番号かステータスフラグの
  可能性）。
- 各TSパケットのPIDフィールド（sync直後2バイトから抽出、例 `0x11b0`=4528、`0x1cf0`=7408）も
  転送ごと・パケットごとに変化しており、複数PIDが混在する実際の多重化TSと矛盾しない。

**コントロール転送 (Endpoint 0, ベンダーリクエスト)**: バルク転送と並行して、ストリーミング中
ずっと約2.5〜3ms周期で以下がリピートしている:

```
bmRequestType=0x40 (Host→Device, Vendor, Device)  bRequest=74 (0x4A)  wValue=0x0000  wIndex=<可変>  wLength=0
bmRequestType=0xc0 (Device→Host, Vendor, Device)   bRequest=78 (0x4E)  wValue=0x0000  wIndex=0       wLength=8  (8バイト応答)
```

`bRequest=74`の`wIndex`は256の倍数付近の値（例: 9472, 9216, 9728, 9984, 10240, 10496, 8192…）を
取り、バルク転送のバッファ充填量やオフセットを通知しているものと推測される。
`bRequest=78`は8バイトのステータス応答を返す。ストリーム停止直前には
`bRequest=79 (0x4F)`（`0x40`, `wLength=0`）も観測されており、`78`と入れ替わりで出現する
——停止・フラッシュ系の別コマンドの可能性がある。

### 続報 (2026-07-25): cdbのライブブレークポイントでコントロール転送の意味を解読

Ghidraで`WinUsb_ControlTransfer`のインポートサンクを辿り（`getReferencesTo`は
EXTERNALシンボルへの参照だけでなく、その先の実体（サンク関数）への参照も別途辿る必要が
あった）、実際に呼び出しているラッパー関数（`mnservice+0x7de00`）を特定。ここへcdbで
ライブブレークポイントを張り（`db rdx L18`でセットアップパケット8バイト+バッファポインタ+
長さをダンプ、`kb 6`でコールスタックも記録）、送出パイプラインテストを実行しながら約800回
ヒットを観測した。

実際にキャプチャされたセットアップパケット（先頭8バイト）:
```
c0 4e 00 00 00 00 08 00   -> bmRequestType=0xc0 bRequest=0x4E(78) wValue=0 wIndex=0 wLength=8
40 4a 00 00 00 26 00 00   -> bmRequestType=0x40 bRequest=0x4A(74) wValue=0 wIndex=0x2600(9728) wLength=0
40 4a 00 00 00 27 00 00   -> (次の呼び出し) wIndex=0x2700(9984) -- 前回から+256
```

コールスタックを遡ってこの2つの呼び出しを行っている関数を特定・デコンパイルしたところ
（`mnservice+0x87920`）、埋め込みログ文字列から**`mhal_modulation.cc`**（変調ハードウェア
抽象化レイヤ）の一部と判明した。ロジックは:

```c
// param_3 = wIndexとして送る値（呼び出し元から渡される）
// param_4 = このプロトコル層関数の出力先ポインタ
FUN_140088050(param_1, &local_40, 0x4a, param_3);      // SET: wIndex=param_3, wLength=0
if (成功) {
    FUN_140088050(param_1, &local_68, 0x4e, 0);         // GET: 8バイト応答
    if (成功) {
        // 応答の先頭4バイトが送信したparam_3と一致するかチェック(ACK確認)
        if (応答先頭4バイト == param_3) {
            *param_4 = 応答の後半4バイト;                // 一致すれば後半4バイトを出力
        } else {
            // 不一致ならエラー (mhal_modulation.cc:207, FailedPreconditionError)
        }
    }
}
```

さらに`param_3`（=wIndexとして送る値）自体の出所を1段階遡ると、複数チャンネルを走査する
ループの中で`*(int*)(チャンネル構造体+0x24)`という、**チャンネルごとの状態フィールド**から
読み出されていることが分かった。

これと`mslicebuffer.cc:50] slice buffer size : [24064:224:5390336]`
（24064×224=5390336ぴったり）を合わせると、全体像は次のように理解できる:

- サービス側はサイズ24064バイト（=MPEG-TS 188バイト×128）のスライスを224個持つ、
  合計5,390,336バイトのリングバッファでTSデータを管理している。
- 各スライスをUSBバルク転送でデバイスに送るのと並行して、**「ここまで書き込んだ」という
  位置（`wIndex`、おそらくバイトオフセットか224スライス中の何らかの単位）をベンダー
  コントロール転送(`bRequest=0x4A`)でデバイスに通知**し、
- 直後に`bRequest=0x4E`でデバイス側の状態を読み出し、**応答の先頭4バイトが送った値と
  一致するかでACK（受理確認）を取り**、後半4バイトから**デバイス側の消費済み位置**などの
  情報を受け取っている。

つまりバルク転送そのものとは別に、**このコントロール転送ペアがリングバッファのフロー
制御（オーバーラン防止のハンドシェイク）を担っている**、という一貫した説明が成立する。

### 続報2 (2026-07-25): 汎用「アドレス設定→読み書き」レジスタバスだと判明

`FUN_140088050`（`0x4a`/`0x4e`/`0x4f`を実際に`WinUsb_ControlTransfer`へ渡している最下層の
ラッパー）の呼び出し元を**全て**洗い出したところ、`mhal_modulation.cc`内に以下の3パターンが
見つかった:

- **単発読み出し** (`mnservice+0x87920`, 上述): `0x4a`でアドレス（wIndex）をセット→
  `0x4e`で1回読み出し（アドレスエコー4バイト+データ4バイト）→エコーが一致すればデータを
  採用。ストリーミング中の周期通知はコレ。
- **ブロック読み出し** (`mnservice+0x87720`): `0x4a`でアドレスを1回セット→`0x4e`を
  `param_5`回ループし、**呼び出しごとに期待アドレス値をインクリメント**しながら連続する
  複数ワードを読み出す。エンディアン変換フラグ(`param_6`)あり。
- **ブロック書き込み** (`mnservice+0x883b0`): `0x4a`でアドレスを1回セット→**`0x4f`を
  `param_5`回ループし、呼び出し元バッファから4バイトずつ読んだ値をそのまま送信**（アドレスは
  自動インクリメントされる想定）。同じくエンディアン変換フラグあり。
- **単発書き込み** (`mnservice+0x88500`): `0x4a`でアドレスをセット→`0x4f`を1回だけ呼んで
  1ワード書き込み。

これにより、当初「リングバッファ専用のフロー制御ハンドシェイク」と解釈していた`0x4a`/`0x4e`は
実際には**汎用的な「アドレス設定＋データ読み書き」のレジスタバス的プロトコル**の一部分
（たまたまストリーミングのリングバッファ位置通知に使われている一事例）だと判明した:

| bRequest | 方向 | 役割 |
|---|---|---|
| `0x4A` (74) | Host→Device (SET) | 対象アドレス/オフセットを`wIndex`にセット |
| `0x4E` (78) | Device→Host (GET, 8バイト) | 読み出し。応答=[セットしたアドレスのエコー4B][そのアドレスのデータ4B]。エコー不一致は多重アクセス競合として扱われエラーになる |
| `0x4F` (79) | Host→Device (SET) | 直前にセットしたアドレスへ4バイトのデータを書き込む（ブロック書き込みでは自動インクリメントで連続ワードを送っている） |

この枠組みなら、公式GUIが送っている`mModulationParam`/`mPSEncodeParam`等の各種プロパティも
最終的にはこの同じレジスタ読み書きバス経由でハードウェアへ反映されていると考えるのが自然
（`CmdChannelStart`のプロパティ群 → `mhal_modulation.cc`が個々のフィールドを対応するレジスタ
アドレスへの`0x4a`+`0x4f`書き込みに変換、という流れが濃厚）。ストリーム停止直前に観測された
単独の`0x4f`も、この枠組みなら「既にセット済みのアドレスへ停止用の値を書き込んだ」で自然に
説明がつく。

### 続報3 (2026-07-25): 実際にレジスタマップを構築 — Frequencyアドレスを確定

`mModulationParam.Frequency`を目立つ値（`600000`）に変更し、`CmdChannelStart`実行中の
コントロール転送をcdbで再キャプチャして、その値がどの「アドレス」に書き込まれるかを
直接突き合わせた。

**重要な発見: 書き込みデータは32bitの生ビッグエンディアン値**（`wValue`/`wIndex`という
USB SETUPパケット本来のフィールド境界は無視し、4バイト目〜7バイト目を単純にBE整数として
埋めている）。`600000 = 0x000927C0`に対し、実際に観測されたバイト列は`00 09 27 C0`——
これはBE表現とバイト単位で完全一致する。アドレス（`0x4a`側の`wIndex`）も同じくBEだと
判明した（後述のPAGain一致で裏付け）。これは前回「wIndexは256刻みで増加するのでLEっぽい」
と推測していたが誤りで、たまたま上位バイトが0のケースだけを見ていたため区別できて
いなかった。

`CmdChannelStart`実行時に観測された実際のアドレス:データ ペア（BE解釈、ISDB-T・
473000kHz(初期値)/600000kHz(テスト値)・Constellation=QPSK・Level=90/PAGain=2/DACGain=-10で
送信時）:

| アドレス (BE) | 書き込みデータ (BE) | 対応（確度） |
|---|---|---|
| `0x1202` | `0x000927C0` = 600000 | **Frequency（確定・2回一致）** |
| `0x1221` | `0x00000002` = 2 | PAGain（一致、確度高） |
| `0x1229` | `0x0000F6F6` | DACGain関連（下位バイトに`0xF6`=-10が2回出現、確度中） |
| `0x1220` | `0x78122901` | 未解読（複合ビットフィールドの可能性） |
| `0x1228` | `0x00000000` | 未解読 |
| `0x1290` | `0x45585402` (ASCII的には"EXT"+0x02) | 未解読 |
| `0x0601`〜`0x0602`, `0x0640`〜`0x0642` | 1〜5の小さい値 | 未解読（別バンク、Constellation等の可能性） |
| `0x0600` | 読み出し→`0x00001000`書き込み→読み出し | 未解読 |

`0x1202`〜`0x1290`台がひとまとまりの「変調・RF電力」レジスタバンクで、`0x0600`〜`0x0642`台は
別のバンク（チャンネル/エンコーダ関連の可能性）と見られる。この手法（既知の値を1つだけ
変えて再キャプチャし、バイト列を直接突き合わせる）は他のフィールド（Constellation・
Bandwidth・FFT等）にもそのまま応用でき、レジスタマップを機械的に拡張していける。

### 未解読・今後の課題

- `0x1220`/`0x1228`/`0x1290`など、まだ値を意図的に変えて突き合わせていないレジスタの意味
- `0x0600`台の別バンクの役割（Constellation/Bandwidth/FFT等、mModulationParamの他フィールドが
  ここに対応する可能性が高い — 同じ「1つだけ値を変えて再キャプチャ」の手法で特定できる）
- ブロック読み書き時の「自動インクリメント」の正確な挙動（本当にアドレス側が自動で
  進むのか、それとも毎回ホスト側が`wIndex`を明示的に増やしているだけなのか）は未確認
- バルク転送先頭3バイトヘッダの意味（このレジスタバスとは別チャンネルなので直接の関係は
  薄いと思われるが未確認）

**安全上の注意**: `mModulationParam.Frequency`は宣言上のwire-protocol範囲が`0..1000000`だが、
実際に`999999`（範囲内）を送ったところ`mnservice.exe`がクラッシュした（デバイス・サービスは
再起動で正常復帰、実害なし）。**宣言されている範囲は実際にハードウェアが受け付ける範囲より
広い**ため、大きく外れた値のテストは要注意（本機はループバック環境のため実害はないが、
クラッシュ自体は再現する）。

これらもGhidra/cdbの組み合わせ（`tools/native_analysis`のスクリプト・手順を流用）で
引き続き掘り下げ可能。生pcap自体はサイズが大きくgitignore対象だが、再取得手順は
上記の通り再現できる。

## キャプチャ手順（案）

1. Wireshark を管理者権限で起動。
2. キャプチャインターフェース一覧から `USBPcap1`（root hub、実際のポート番号は
   `Get-PnpDevice` 等で事前に確認）を選択。
3. フィルタ例: `usb.device_address == <XHEAD-USBのアドレス>`
4. キャプチャ開始 → `xhead_studio.exe` で以下の操作を行い、対応するUSBトランザクションを記録:
   - アプリ起動直後（列挙・ベンダーコマンドでの初期化）
   - チャンネル/変調パラメータの変更
   - 放送開始 (`CmdChannelStart` 相当)
   - 放送停止
   - PowerLevel変更（連続的な値なのでコマンドの差分が追いやすい）
5. `.pcapng` として `captures/usb/` に保存（Gitには含めない。解析用に手元で保持）。

## 解析の視点

- Bulk転送（映像データ本体=TS）とControl転送（設定コマンド）を分離する。
- Controlトランザクション (`bmRequestType`/`bRequest`/`wValue`/`wIndex`) の一覧を取り、
  GUIでのパラメータ変更操作とタイムスタンプを突き合わせて意味を推定する。
- `mnFirmwareUSB.cs` / `mnControlCode.cs`（デコンパイル済み, `decompiled/mnClientDotNet/mnFramework/`）
  に `Progress` / `Param` / `Firmware` という制御コード種別があり、ファームウェア書き換えも
  同じUSBチャンネル経由と推測される。ファームウェア関連のキャプチャ・改変は特に慎重に扱うこと
  （実機を壊すリスクがあるため、まずは読み取り専用の観測に留める）。
