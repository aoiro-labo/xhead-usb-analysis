# USBプロトコル解析メモ

## 対象

`mnservice.exe`（ネイティブサービス）が XHEAD-USB 実機と行う生のUSB通信。
gRPC (`docs/protocol/`) はあくまで **PC内の GUI⇔サービス間** の通信であり、実機との
通信プロトコルとは別レイヤ。ここが未解析の最後のブラックボックス。

**2026-07-25追記**: ここで解読したレジスタバスプロトコルを実際に実装し、`mnservice.exe`を
一切経由せず実機へ直接読み書きすることに成功した（[tools/direct_usb](../direct_usb)）。
読み取り専用スキャンで「休止時」のレジスタ値を初めて直接観測でき、`0x1220`/`0x1290`/
`0x0629`/`0x0600`が静的な設定値ではなく動作中のみ意味を持つステータス/トリガー系
レジスタらしいという新しい手がかりも得られた。詳細は`tools/direct_usb/README.md`を参照。

## 現状の環境

- 実機は `VID_17A7&PID_0008` として認識。
- **確認済み(2026-07-24)**: ドライバクラスが **libusbk devices** (provider libusbK, v3.1.0.0,
  `oem122.inf`) になっており、公式アプリはこの状態で実機接続に失敗する
  （`XHEAD Studio: XHEAD-USBの接続に失敗しました。` ダイアログ）。
  - デバイスの `CompatibleID` に `USB\MS_COMP_WINUSB` が含まれており、これはデバイス
    ファームウェア自身がMS OS Descriptor経由のWinUSB自動バインドに対応していることを示す。
    つまり本来のドライバは **WinUSB**（Microsoft純正・署名済み）であり、専用ベンダードライバ
    ではないと推定される。
  - `C:\sdrsharp-x86\zadig.exe` がこのマシンに存在しており、RTL-SDR用ドライバ導入時に
    誤ってXHEAD-USBの方のドライバもlibusbKへ差し替えてしまったと推測される。
  - **対処法**: デバイスマネージャーでドライバを削除→USB抜き差しで再列挙させ、WinUSBへの
    自動バインドを待つ。または Zadig で明示的に XHEAD-USB → WinUSB を選んで
    "Replace Driver" する（RTL-SDR側のデバイスと誤選択しないよう要注意）。
  - `mnservice.exe` は gRPC (localhost:50051) 自体は正常に待受けており、この問題は
    純粋に `mnservice.exe` ⇔ 実機のUSBオープンの失敗（WinUSB API呼び出し失敗）と考えられる。
    自作ツール (`tools/custom_sender`) で `connectService` した際も
    `Status=StatusOffline` が返り、実機非接続状態と整合する。
- Wireshark + USBPcap はインストール済み (`C:\Program Files\Wireshark`, `C:\Program Files\USBPcap`)。

## 結果 (2026-07-25): 実データのキャプチャに成功、基本フレーミングを解読

### 経緯: 最初の2回は謎の空振り、3回目（別ハブへの挿し替え後）で成功

`tshark`（管理者権限で実行、`IsInRole(Administrator)`で確認済み）で`\\.\USBPcap3`
（実機が列挙されているルートハブ）を対象に、`mnservice.exe`をキャプチャ開始後に再起動→
自作ツールでフル送出パイプラインを実行、という手順を試したが、**最初の2回（同一USBポート/
同一デバイスインスタンスID `B103140916AB` のまま）は実データ転送が一切キャプチャできず**、
`GET DESCRIPTOR`/`SET CONFIGURATION`の6パケットのみだった。これはキャプチャ開始時に
接続済みの全USBデバイスに対して一律に発生する合成/注入パケットで、実際のI/Oではないと
判明した（アドレス1〜19の全デバイスで全く同じ6パケットパターンを確認）。ルートハブ選択
ミス・Isochronous起因・管理者権限不足はいずれも根拠を確認して否定した。

その後、**ユーザーが実機のケーブルを物理的に別のUSBハブへ挿し替えた**ところ（同じ
`USBPcap3`＝同じホストコントローラ配下だが、新しいポート番号・新しいUSBアドレス`3.48`で
再列挙）、**同じ手順で今度は実データが正常にキャプチャできた**（コントロール転送1242
パケット、バルク転送359パケット）。原因はデバイス移動そのものというより、**新規の完全な
USB列挙**が発生したことだと考えられる（同一デバイスインスタンスのまま`mnservice.exe`だけを
再起動しても、WinUSBパイプハンドルが何らかの理由でUSBPcapから見えない状態になっていた
可能性がある）。同じ症状が再発した場合は、デバイスを一度物理的に抜き差しして完全な
再列挙を発生させるのが有効な回避策と考えられる。

### 判明したフレーミング

**バルク転送 (Endpoint 0x81 IN / 0x01 OUT, `bmAttributes=0x02`=BULK)**:

- 転送サイズは一貫して **24064バイト** = `mnservice.exe`の自ログ
  `mslicebuffer.cc:50] slice buffer size : [24064:224:5390336]`の先頭値と完全一致。
  128 × 188 = 24064 で、MPEG-TSパケット（188バイト）128個分ぴったりに相当する。
- ペイロードをバイト単位で調べたところ、**オフセット3, 191, 379, 567, ...
  （3 + 188×n、stride=188で完全に規則的）に`0x47`（MPEG-TS同期バイト）が並んでいる**ことを
  確認した。つまり中身は生のMPEG-TSパケット列そのもの。
- ただし各転送の先頭3バイトだけは同期バイトの前にある「ヘッダ」で、複数の転送を比較すると
  値が転送ごとに変化する（例: `10 00 40`, `14 12 40`, `16 12 40`, `1c 12 40`, `11 01 41`...）。
  単純な単調増加カウンタではなさそうで、意味は未解読（シーケンス番号かステータスフラグの
  可能性）。
- 各TSパケットのPIDフィールド（sync直後2バイトから抽出、例 `0x11b0`=4528、`0x1cf0`=7408）も
  転送ごと・パケットごとに変化しており、複数PIDが混在する実際の多重化TSと矛盾しない。

**コントロール転送 (Endpoint 0, ベンダーリクエスト)**: バルク転送と並行して、ストリーミング中
ずっと約2.5〜3ms周期で以下がリピートしている:

```
bmRequestType=0x40 (Host→Device, Vendor, Device)  bRequest=74 (0x4A)  wValue=0x0000  wIndex=<可変>  wLength=0
bmRequestType=0xc0 (Device→Host, Vendor, Device)   bRequest=78 (0x4E)  wValue=0x0000  wIndex=0       wLength=8  (8バイト応答)
```

`bRequest=74`の`wIndex`は256の倍数付近の値（例: 9472, 9216, 9728, 9984, 10240, 10496, 8192…）を
取り、バルク転送のバッファ充填量やオフセットを通知しているものと推測される。
`bRequest=78`は8バイトのステータス応答を返す。ストリーム停止直前には
`bRequest=79 (0x4F)`（`0x40`, `wLength=0`）も観測されており、`78`と入れ替わりで出現する
——停止・フラッシュ系の別コマンドの可能性がある。

### 続報 (2026-07-25): cdbのライブブレークポイントでコントロール転送の意味を解読

Ghidraで`WinUsb_ControlTransfer`のインポートサンクを辿り（`getReferencesTo`は
EXTERNALシンボルへの参照だけでなく、その先の実体（サンク関数）への参照も別途辿る必要が
あった）、実際に呼び出しているラッパー関数（`mnservice+0x7de00`）を特定。ここへcdbで
ライブブレークポイントを張り（`db rdx L18`でセットアップパケット8バイト+バッファポインタ+
長さをダンプ、`kb 6`でコールスタックも記録）、送出パイプラインテストを実行しながら約800回
ヒットを観測した。

実際にキャプチャされたセットアップパケット（先頭8バイト）:
```
c0 4e 00 00 00 00 08 00   -> bmRequestType=0xc0 bRequest=0x4E(78) wValue=0 wIndex=0 wLength=8
40 4a 00 00 00 26 00 00   -> bmRequestType=0x40 bRequest=0x4A(74) wValue=0 wIndex=0x2600(9728) wLength=0
40 4a 00 00 00 27 00 00   -> (次の呼び出し) wIndex=0x2700(9984) -- 前回から+256
```

コールスタックを遡ってこの2つの呼び出しを行っている関数を特定・デコンパイルしたところ
（`mnservice+0x87920`）、埋め込みログ文字列から**`mhal_modulation.cc`**（変調ハードウェア
抽象化レイヤ）の一部と判明した。ロジックは:

```c
// param_3 = wIndexとして送る値（呼び出し元から渡される）
// param_4 = このプロトコル層関数の出力先ポインタ
FUN_140088050(param_1, &local_40, 0x4a, param_3);      // SET: wIndex=param_3, wLength=0
if (成功) {
    FUN_140088050(param_1, &local_68, 0x4e, 0);         // GET: 8バイト応答
    if (成功) {
        // 応答の先頭4バイトが送信したparam_3と一致するかチェック(ACK確認)
        if (応答先頭4バイト == param_3) {
            *param_4 = 応答の後半4バイト;                // 一致すれば後半4バイトを出力
        } else {
            // 不一致ならエラー (mhal_modulation.cc:207, FailedPreconditionError)
        }
    }
}
```

さらに`param_3`（=wIndexとして送る値）自体の出所を1段階遡ると、複数チャンネルを走査する
ループの中で`*(int*)(チャンネル構造体+0x24)`という、**チャンネルごとの状態フィールド**から
読み出されていることが分かった。

これと`mslicebuffer.cc:50] slice buffer size : [24064:224:5390336]`
（24064×224=5390336ぴったり）を合わせると、全体像は次のように理解できる:

- サービス側はサイズ24064バイト（=MPEG-TS 188バイト×128）のスライスを224個持つ、
  合計5,390,336バイトのリングバッファでTSデータを管理している。
- 各スライスをUSBバルク転送でデバイスに送るのと並行して、**「ここまで書き込んだ」という
  位置（`wIndex`、おそらくバイトオフセットか224スライス中の何らかの単位）をベンダー
  コントロール転送(`bRequest=0x4A`)でデバイスに通知**し、
- 直後に`bRequest=0x4E`でデバイス側の状態を読み出し、**応答の先頭4バイトが送った値と
  一致するかでACK（受理確認）を取り**、後半4バイトから**デバイス側の消費済み位置**などの
  情報を受け取っている。

つまりバルク転送そのものとは別に、**このコントロール転送ペアがリングバッファのフロー
制御（オーバーラン防止のハンドシェイク）を担っている**、という一貫した説明が成立する。

### 続報2 (2026-07-25): 汎用「アドレス設定→読み書き」レジスタバスだと判明

`FUN_140088050`（`0x4a`/`0x4e`/`0x4f`を実際に`WinUsb_ControlTransfer`へ渡している最下層の
ラッパー）の呼び出し元を**全て**洗い出したところ、`mhal_modulation.cc`内に以下の3パターンが
見つかった:

- **単発読み出し** (`mnservice+0x87920`, 上述): `0x4a`でアドレス（wIndex）をセット→
  `0x4e`で1回読み出し（アドレスエコー4バイト+データ4バイト）→エコーが一致すればデータを
  採用。ストリーミング中の周期通知はコレ。
- **ブロック読み出し** (`mnservice+0x87720`): `0x4a`でアドレスを1回セット→`0x4e`を
  `param_5`回ループし、**呼び出しごとに期待アドレス値をインクリメント**しながら連続する
  複数ワードを読み出す。エンディアン変換フラグ(`param_6`)あり。
- **ブロック書き込み** (`mnservice+0x883b0`): `0x4a`でアドレスを1回セット→**`0x4f`を
  `param_5`回ループし、呼び出し元バッファから4バイトずつ読んだ値をそのまま送信**（アドレスは
  自動インクリメントされる想定）。同じくエンディアン変換フラグあり。
- **単発書き込み** (`mnservice+0x88500`): `0x4a`でアドレスをセット→`0x4f`を1回だけ呼んで
  1ワード書き込み。

これにより、当初「リングバッファ専用のフロー制御ハンドシェイク」と解釈していた`0x4a`/`0x4e`は
実際には**汎用的な「アドレス設定＋データ読み書き」のレジスタバス的プロトコル**の一部分
（たまたまストリーミングのリングバッファ位置通知に使われている一事例）だと判明した:

| bRequest | 方向 | 役割 |
|---|---|---|
| `0x4A` (74) | Host→Device (SET) | 対象アドレス/オフセットを`wIndex`にセット |
| `0x4E` (78) | Device→Host (GET, 8バイト) | 読み出し。応答=[セットしたアドレスのエコー4B][そのアドレスのデータ4B]。エコー不一致は多重アクセス競合として扱われエラーになる |
| `0x4F` (79) | Host→Device (SET) | 直前にセットしたアドレスへ4バイトのデータを書き込む（ブロック書き込みでは自動インクリメントで連続ワードを送っている） |

この枠組みなら、公式GUIが送っている`mModulationParam`/`mPSEncodeParam`等の各種プロパティも
最終的にはこの同じレジスタ読み書きバス経由でハードウェアへ反映されていると考えるのが自然
（`CmdChannelStart`のプロパティ群 → `mhal_modulation.cc`が個々のフィールドを対応するレジスタ
アドレスへの`0x4a`+`0x4f`書き込みに変換、という流れが濃厚）。ストリーム停止直前に観測された
単独の`0x4f`も、この枠組みなら「既にセット済みのアドレスへ停止用の値を書き込んだ」で自然に
説明がつく。

### 続報3 (2026-07-25): 実際にレジスタマップを構築 — Frequencyアドレスを確定

`mModulationParam.Frequency`を目立つ値（`600000`）に変更し、`CmdChannelStart`実行中の
コントロール転送をcdbで再キャプチャして、その値がどの「アドレス」に書き込まれるかを
直接突き合わせた。

**重要な発見: 書き込みデータは32bitの生ビッグエンディアン値**（`wValue`/`wIndex`という
USB SETUPパケット本来のフィールド境界は無視し、4バイト目〜7バイト目を単純にBE整数として
埋めている）。`600000 = 0x000927C0`に対し、実際に観測されたバイト列は`00 09 27 C0`——
これはBE表現とバイト単位で完全一致する。アドレス（`0x4a`側の`wIndex`）も同じくBEだと
判明した（後述のPAGain一致で裏付け）。これは前回「wIndexは256刻みで増加するのでLEっぽい」
と推測していたが誤りで、たまたま上位バイトが0のケースだけを見ていたため区別できて
いなかった。

`CmdChannelStart`実行時に観測された実際のアドレス:データ ペア（BE解釈、ISDB-T・
473000kHz(初期値)/600000kHz(テスト値)・Constellation=QPSK・Level=90/PAGain=2/DACGain=-10で
送信時）:

| アドレス (BE) | 書き込みデータ (BE) | 対応（確度） |
|---|---|---|
| `0x1202` | `0x000927C0` = 600000 | **Frequency（確定・2回一致、続報3）** |
| `0x1229` | `0x0000F6F6` | **DACGain（確定、続報5でデコンパイルにより確認）** |
| `0x1221` | `0x00000002` = 2 | ~~PAGain~~ **誤り、続報5で訂正**（下記参照） |
| `0x1220` | `0x78122901` | **固定マジック値（確定、続報5）**。おそらくcommit/latchトリガー |
| `0x1228` | `0x00000000` | **固定値0（確定、続報5）**。未使用フィールドの可能性 |
| `0x1290` | `0x45585402` (ASCII的には"EXT"+0x02) | 下位ニブルが可変、上位24bitは固定"EXT"タグ（続報5） |
| `0x0601`〜`0x0602`, `0x0640`〜`0x0642` | 1〜5の小さい値 | 別バンク。**安定した本物のレジスタと判明（続報7）**、意味は未特定 |
| `0x0600` | 読み出し→`0x00001000`書き込み→読み出し | 同上 |
| `0x0684`/`0x0690`/`0x0691`/`0x0692`/`0x0693`/`0x0694` | 可変 | **Bandwidth/Constellation/FFT/GuardInterval/CodeRate/TimeInterleavce（続報7で確定・完全なマップ化）** |

`0x1202`〜`0x1290`台が「Frequency・RF電力」レジスタバンク、`0x0600`〜`0x0694`台が
「その他の変調パラメータ（Constellation/Bandwidth/FFT/CodeRate/GuardInterval/
TimeInterleavce等）」レジスタバンクという、2つの安定したバンクに分かれている
（詳細・完全な対応表は続報7）。

### 続報5 (2026-07-25): デコンパイルでRF電力書き込みの実装を直接確認、一部訂正

`0x1220`/`0x1221`/`0x1228`/`0x1229`/`0x1290`への書き込みを行っている関数
（`FUN_140088500`＝単発書き込みヘルパー）へcdbで直接ブレークポイントを張り（`rcx`/`r8`
(アドレス)/`r9`(データ)を直接ダンプ、hex手動デコード不要）、コールスタックを遡って
実際の呼び出し元関数`FUN_14039ba70`を特定・デコンパイルした。さらにその上位の呼び出し元
`FUN_14009c540`に埋め込まれたログ文字列`"adjust power : [%02x:%02x]"`
(`mpegasys_output.cc:0x104`) から、これが**まさに`adjust power`ログを出している関数
そのもの**と確定できた。

**事実（デコンパイル結果から直接確認）**:

- ログの引数は`*(param_1+0x283)`（DACGain）→`*(param_1+0x282)`（PAGain）の順で渡されており、
  ログ書式`"[%02x:%02x]"`と合わせると出力は`[DACGain:PAGain]`。実測ログ`[f6:02]`
  （DACGain=-10=0xf6、PAGain=2）と一致 — **DACGain/PAGainのソースフィールドを確定**。
- `0x1229`への書き込み値は、DACGainバイト(D)を`(D<<8)|D`の形で組み立てたもの
  （同じバイトを上位・下位2バイトに重複して詰めている）。実測`0xF6F6`と完全に整合 —
  **0x1229=DACGain registerと確定**。
- `0x1228`への書き込み値は、コード上**常に固定で`0`**（呼び出し元で初期化されたまま
  変更されない）。PAGain/DACGain以外の値からは独立しており、フィールドとしては未使用か、
  今回のテストで使われない別モード用の可能性。
- **`0x1221`は当初「PAGainと一致」としていたが誤りだった**。デコンパイル結果では、
  この値は呼び出し元コードで**リテラル定数`2`としてハードコードされており、
  クライアントから送ったPAGain値とは無関係**。たまたま今回のテストでPAGain=2を
  指定していたため値が一致して見えただけ。実際のPAGain送信経路は別にある
  （後述、未解読）。
- `0x1220`への書き込みは、**条件分岐の外側で常に実行される、コード中に直書きされた
  固定マジック値`0x78122901`**。他の全レジスタ書き込み（0x1228/0x1229/0x1221/
  条件次第で0x1280-0x1283/0x1290）が終わった**最後に必ず送信される**という位置づけから、
  個別の設定値ではなく「ここまでの設定を確定・反映させるcommit/latchトリガー」である
  可能性が高い（これは推測、未確証）。
- `0x1290`は`0x45585400 | (下位4bit)`という形で組み立てられており、上位24bitは常に
  固定（ASCII的に"EXT"と読める）、下位4bitだけが可変。この可変部分の実際のソースは
  まだ追えていない。
- コード上には、`(param_3のオフセット4の値) & 1`が真の場合だけ実行される
  **`0x1280`〜`0x1283`への書き込みブロックが別途存在する**が、このオフセット4の値は
  上述の通り常にリテラル`2`（`2 & 1 == 0`）なので、**通常の`mPSRFPowerAdjust`経由の
  操作ではこのブロックには絶対に到達しない**。クライアントから送ったPAGain
  （`param_1+0x282`由来）は、この関数内では**ログ出力とキャッシュ保存
  （`param_1+0x60/0x68/0x70`への保存、恐らく次回呼び出し時の差分検出用）にしか
  使われておらず、観測した範囲のどのレジスタにも書き込まれていない**。

**推測（未確証、事実と混同しないこと）**:

- PAGainの実際の書き込み先は、上記の`0x1280`〜`0x1283`ブロック（`&1`ビットが立った別の
  呼び出し経路）にある可能性が高いが未確認。gRPC側の`mPSRFPowerAdjust`以外の何らかの
  トリガー（別モード、ファームウェア設定、等）でこのビットが立つのかもしれない。
- `0x1290`の下位4bit（今回観測値=2）は、`mModulationParam.Mode`
  （ISDB_T/DVB_T/ATSC等の選択）に対応する「チップ内部モードID」ではないか、というのが
  現時点での仮説。ISDB_T選択時に2が送られていることと、この位置づけ（"EXT"+モード番号
  らしき構造）が符合するが、他のMode値で実際に試して確認したわけではない。
- `0x1220`の固定値`0x78122901`はコミット/ラッチトリガーという解釈が最も自然だと考えるが、
  日付や版数を符号化した識別子である可能性も否定はできない（`0x78`=120は月として
  成立しないため、日付エンコードの可能性は低いと判断している）。

### 続報6 (2026-07-25): さらに深掘り — PAGainは行き止まり、バルクヘッダはUSBPcapの不調で再挑戦できず

**PAGainの送信先を追った結果（事実）**: `FUN_14039ba70`（RF電力書き込み関数）と、その唯一の
呼び出し元`FUN_14009c540`について、Ghidraで**全ての**呼び出し元を再検索した。どちらも
呼び出し元は1箇所ずつしかなく（`FUN_14039ba70`←`FUN_14009c540`←`FUN_14009d5e0`）、
`0x1280`〜`0x1283`ブロックを実際に有効化する別の呼び出し経路は見つからなかった。
`FUN_14009c540`が`param_3+4`に渡す値は常にリテラル`2`なので、少なくとも今回逆アセンブルで
辿れた範囲では**PAGainの書き込み先は特定できなかった**（未解読のまま）。これ以上追うには
vtable経由の別の呼び出し元（RTTI解析）かファームウェア側の解析が必要と考えられる。

**バルク転送の3バイトヘッダを追加調査しようとしたが、USBPcapが2度目の「実データが
見えない」状態に陥った（事実）**: 前回の物理ハブ挿し替えで解決したはずの症状
（[続報1](#結果-2026-07-25-実データのキャプチャに成功基本フレーミングを解読)参照）が、
同じ物理ポートのまま`mnservice.exe`の再起動を何度も繰り返した後に**再発**した
（合成注入パケット3個のみで実データなし）。これは「デバイスインスタンス／ポートを変えずに
`mnservice.exe`の起動・終了を繰り返すと、いずれUSBPcapが実データを見失う」という仮説を
補強する2件目の実例。ユーザーへ再度の物理抜き差しを頼むほどではないと判断し、
このセッションでのバルクヘッダ深掘りは中断した。次回このテーマに戻るときは、
まず物理抜き差しから始めるとよい。

**代わりに静的解析でスライスバッファの実装を確認できた（事実）**: `mslicebuffer.cc`内の
`"slice buffer size"`ログ文字列からアロケータ関数`FUN_14038ac60`
（`mslicebuffer.cc:0x32`）を特定・デコンパイルした。`param_3`=スライスサイズ、
`param_4`=スライス数を受け取り、`malloc(param_3*param_4)`で一括確保し、
開始/終了/書き込み/読み出しポインタ（`param_1+0x78/0x80/0x88/0x90`）とスライスサイズ・
スライス数（`param_1+0x6c/0x70`）をオブジェクトに保存している。これは以前ログ行から
推測していた「24064バイト×224スライス＝5,390,336バイトのリングバッファ」という理解を
**ソースコードレベルで直接裏付ける**。ただし、この関数はアロケータであり、個々のスライスへの
書き込み処理（3バイトヘッダを付与している箇所）はまだ見つけられていない——USBPcapで
実データが取れるようになったら、`mslicebuffer.cc`内の他の関数（アロケータのすぐ近くにある
はず）を静的に洗い出すのと、ライブキャプチャでの突き合わせを組み合わせるのが近道と思われる。

### 続報7 (2026-07-25): 深掘りの結果、ISDB-T変調パラメータのレジスタマップがほぼ完成

**手法の改善（事実）**: 単発書き込みヘルパー(`FUN_140088500`)への生メモリダンプ
(`db rdx L18`)を手動で16進デコードする代わりに、`bu mnservice+0x88500 "r rcx; r r8; r r9; ...`
のようにブレークポイントコマンドで**引数レジスタを直接ダンプ**する方式に切り替えた
（x64呼び出し規約: 第3引数`address`=r8, 第4引数`data`=r9）。この方が転記ミスが起きようが
なく、結果として続報4の「セッションごとにランダム」という結論は誤りだったと判明した。

**やり直した実験と結果（事実、いずれもクラッシュなし・デバイス健全性確認済み）**:
`mModulationParam`の各フィールドを1つずつ、確認済みで安全な値に変えては
`CmdChannelStart`をcdb監視下で再実行し、`0x06xx`台の値がどう変化するかを直接比較した:

| 変更したフィールド | 変更前→後 | 変化したアドレス | 変化前→後 |
|---|---|---|---|
| Constellation | QAM64(3)→QPSK(1) | `0x0690` | `3`→`1` |
| Bandwidth | 6→8 | `0x0684` | `6`→`8` |
| FFT | `_8k`(1)→`_2k`(0) | `0x0691` | `1`→`0` |
| CodeRate | CR_5_6(3)→CR_1_2(0) | `0x0693` | `3`→`0` |

いずれも**変更した値がバイト単位で完全一致**しており、他の全アドレスは変更前後で
不変だった（=真に安定したレジスタであることの直接証拠）。GuardIntervalと
TimeInterleavceはデフォルト値がともに`3`で他フィールドと重複するため直接の
値変更テストはしていないが、残った2つの安定アドレス`0x0692`(常時`1`)・
`0x0694`(常時`3`)への消去法で対応付けた（**確度は高いが、直接の値変更確認はまだ**）。

**確定した変調パラメータ・レジスタマップ**:

| アドレス (BE) | フィールド | 確度 |
|---|---|---|
| `0x1202` | Frequency | 確定（値変更で直接確認、続報3） |
| `0x0684` | Bandwidth | **確定（値変更で直接確認）** |
| `0x0690` | Constellation | **確定（値変更で直接確認）** |
| `0x0691` | FFT | **確定（値変更で直接確認）** |
| `0x0692` | GuardInterval | 高確度（消去法、直接確認は未実施） |
| `0x0693` | CodeRate | **確定（値変更で直接確認）** |
| `0x0694` | TimeInterleavce | 高確度（消去法、直接確認は未実施） |

**未解読のまま残っている同バンクのアドレス**（値は今回のテスト条件下で安定して観測されたもの、
意味は未特定）: `0x0600`(読み書き混在: 1→2→0x1000→0x2000)、`0x0601`=5、`0x0602`=1、
`0x0629`=0、`0x0640`=3、`0x0641`=1、`0x0642`=0、`0x0680`=5、`0x0681`=1、`0x0682`=0、
`0x0683`=0。当初は`mMTSChannelParam`/`mPSEncodeParam`等の他プロパティ群が対応するのでは
と予想していたが、続報8で`mMTSChannelParam.RegionID`を実際にテストした結果、この予想は
外れた（詳細は続報8）。

**【追記】`0x0600`と`0x0629`はその後解明された——続報9でライフサイクル全体を確認し、
`0x0600`は`0`(idle)→`0x1000`(ChannelStart中、Frequency書き込み直後)→`1`(ChannelStart、

判明。`0x0629`はリングバッファの占有量（キュー深度）ステータスの可能性が高いと判明した。
さらに`docs/protocol/modulation_capabilities.md`「続報15」で、`0x0600=0x2000`を

これで`tools/direct_usb`経由での「送出停止」も実現している。他のアドレス（`0x0601`/`0x0602`/
`0x0640`〜`0x0642`/`0x0680`〜`0x0683`）は引き続き意味未特定。

これでISDB-T変調に直接関わる主要パラメータ（周波数・変調方式・帯域幅・FFTサイズ・
符号化率・ガードインターバル・時間インターリーブ）のレジスタアドレスがほぼ出揃った。
自前実装（vendor DLL非依存でXHEAD-USBを直接制御するプログラム）を書く場合、この
テーブルとこれまでの続報1〜3で解読したフレーミング（アドレス設定→データ読み書きの
プロトコル）があれば、少なくとも変調パラメータの設定だけは`mnservice.exe`を経由せず
直接実装できる可能性が高い。

### 続報8 (2026-07-26): `mMTSChannelParam`はレジスタバスに一切現れない

残り6グループのうち唯一まだ値変更テストをしていなかった`mMTSChannelParam`について、
`RegionID`（`custom_sender`のプロパティダンプで確認: FieldID=4, デフォルト23=日本,
範囲0..63）を目立つマーカー値`55`(0x37)に変更して`CmdChannelStart`を実行、
[tools/native_analysis](../native_analysis)の確立済み手法（`mnservice+0x88500`/
`0x883b0`への書き込みブレークポイントで`rcx`/`r8`/`r9`を直接ダンプ）で全書き込みを
キャプチャした。

**結果: `0x37`という値は、書き込まれた約30個のレジスタのどこにも一切現れなかった**。
それどころか、書き込まれたアドレス・値の並び自体が、これまでのFrequency/Constellation/
Bandwidth/FFT/CodeRateマーカーテストで確認済みの標準シーケンス（続報7参照）と**完全に
同一**だった——`RegionID`用に新しく発生した書き込みが1つもない。パイプライン自体は
`ChannelStart(early): ResultSuccess`→`ProgramApply: ResultSuccess`→
`SourceStart: StatusRunning`と正常に完走しており、値の受理自体には問題がなかった
(実機は終始健全)。

**結論**: `mMTSChannelParam.RegionID`（および、恐らく`mMTSChannelParam`グループ全体）は
変調器のレジスタバスを一切経由しない。ARIB地域識別コードという性質上、これは
TS多重化・PSI/SI生成に関わるソフトウェア側のパラメータであり、RF変調そのものを担う
ハードウェア（`mhal_modulation.cc`が触るレジスタ群）には無関係、という解釈が自然。

**【2026-07-26追記→さらに訂正】** 同日後半、`mMTSChannelParam`の別フィールド`BroadcasterID`
を明示的に設定するテストで`ChannelStart`が`mnservice.exe`をハングさせる問題を発見し
（`docs/protocol/modulation_capabilities.md`「続報14」）、一時的にこの「安全」という結論に
疑いを持ったが、**同日夜にさらに検証した結果、そのハングはプロパティ/フィールドの問題では
なく、長時間の強制終了・生レジスタ操作の繰り返しによるUSB接続そのものの劣化が原因**だと
判明した（物理的な抜き差し1回で解消、詳細は同ファイル「続報14」の訂正追記を参照）。
この`RegionID`単体テストの「安全」という結論は変わらず有効——`mMTSChannelParam`グループの
フィールドを触ること自体は問題ない。

これにより、残っている未解読アドレス（`0x0600`台の一部・`0x0629`・`0x0640`台・`0x0680`台）
が`mMTSChannelParam`/`mPSEncodeParam`由来という当初の予想は**否定された**——少なくとも
`mMTSChannelParam`は完全に除外できる。これら全てのマーカーテストを通じて、これらのアドレスは
**送信するプロパティの値を何に変えても一切変化しなかった**という点も合わせると、固定の
ハードウェア初期化・立ち上げ用定数（設定可能なチャンネルパラメータとは無関係な、チップ側の
決め打ちシーケンス）である可能性が高いという見方に傾いている（推測、未確定）。
`mPSEncodeParam`（映像解像度・PID等のTSエンコーダ設定）についても同様に、変調ハードウェアとは
別レイヤの話である可能性が高く、以後この方向の追加テストは行っていない。

### 続報9 (2026-07-26): フルライフサイクルキャプチャで新たなレジスタ帯と`0x0629`/`0x0600`の正体に迫る

続報8までは`CmdChannelStart`単発の書き込みバーストしかキャプチャしていなかった。今回は
`custom_sender`のフルパイプラインテスト（`ChannelStart`→`ProgramApply`→`SourceStart`で
実際のデスクトップキャプチャ映像を8秒間流す→`ChannelStop`）を丸ごとcdbでキャプチャし、
書き込みブレークポイント（`mnservice+0x88500`/`0x883b0`）に加えて、単発読み出しの
ラッパー関数（`mnservice+0x87920`、続報「cdbのライブブレークポイントでコントロール転送の
意味を解読」で特定済み）にも初めてブレークポイントを張った。最初は引数（アドレス）だけを
見ていたが、`r $t0 = r8; r $t1 = r9; gu; .printf "READ addr=0x%x -> data=0x%x\n", $t0, poi($t1)`
という形に改良し、`gu`(関数のreturnまで実行)後に出力バッファの中身を読むことで、
**読み出しの実際の値**まで取得できるようにした。

**新発見1: `0x0020`〜`0x0029`という第三のレジスタ帯を発見。デバイス接続直後に一度だけ
ブロック読み出しされる「デバイス識別/Transform」情報らしい**:

```
0x25 -> 0x02070816
0x24 -> 0x00010300
0x26 -> 0xf8000002
0x27 -> 0x01000102
0x28 -> 0x00370007
0x29 -> 0x0000ff03
0x20 -> 0xff000001   (このあとも値が変化する、後述)
```

このブロック読み出し直後に、ネイティブログが
`mwinusb.cc:315] modulation [Transform :02070816:A3]`と出力しており、
**`0x25`の読み取り値`0x02070816`とログの`02070816`が完全一致**した。つまり`0x25`は
`mwinusb.cc`が"Transform"と呼ぶ値そのもの。`mnbridge.cc`の`open channel`ログの直前に
実行されるタイミングから見て、この一帯はデバイス接続時に一度だけ読む**デバイス識別・
互換性確認用の情報ブロック**である可能性が高い（推測）。`0x20`だけは後の観測でも値が
変化しており（後述）、この帯の中で唯一「静的な識別情報」ではなく「動的な状態」を
持つ可能性がある。

**新発見2: `0x1280`〜`0x1283`は実際に読み出されている**。過去の静的解析（続報5・続報6）で
「この4アドレスへの書き込みブロックは常にfalseでゲートされ、通常経路では絶対に到達しない」
と結論していたが、これは**書き込み**についての話であり、**読み出し**は別の、常に実行される
経路で行われていたことが今回判明した。RF電力設定バースト（`0x1228`/`0x1229`書き込みの直前）
のタイミングで`0x1280`=`0xa`、`0x1281`=`0x88`、`0x1282`=`0x0`、`0x1283`=`0x4`という値を
確認。恐らくPA（パワーアンプ）の工場較正データやステータスフラグを読み取り、書き込み判断の
参考にしている（が、少なくとも今回のテスト条件では実際に書き戻される様子はなかった）。
PAGain（続報5・6で行き止まりになっていた）の手がかりとして再考の余地がある。

**新発見3: `0x0629`は継続的にポーリングされる、値が変動するステータスレジスタ —
リングバッファ占有量説を補強**。8秒間のストリーミング保持中、`0x0629`への書き込み
（常に`0`)と読み出しが約19ms間隔でペアになって繰り返された（413回ずつ）。実際の読み取り値は
一定ではなく、`0x7`〜`0x1d8`(7〜472)の範囲で絶えず変動していた。これは3つの異なる文脈での
観測と綺麗に符合する:

| 文脈 | `0x0629`の値 |
|---|---|
| 完全な待機状態（`mnservice.exe`が`ChannelStart`を一度も実行していない） | `0x1B7`=439（安定） |
| レジスタ設定のみ実行、バルク転送は一切送っていない（`tools/direct_usb --configure`） | `0`（安定） |
| 実際にTSデータが継続的に流れている最中（今回） | `0x7`〜`0x1d8`の範囲で絶えず変動 |

「データが全く流れていなければ0、実際にデータが出入りしていれば変動する」という挙動は、
**リングバッファの占有量（キュー深度）を示すステータスレジスタ**という解釈と非常によく
符合する（推測だが、これまでで最も裏付けの強い仮説）。単なる待機時の`439`という値は
デバイス再起動をまたいで持ち越された残留状態か、もしくは別の意味を持つ可能性もあり、
完全には説明しきれていない。

**【追記・2026-07-27】** `tools/direct_usb`（フローコントロール通知`0x4A`/`0x4E`を伴わない
生のバルクOUT送信のみ）で同じ`0x0629=0`書き込み→読み取りのペアパターンを再現し、65MB前後の
TSデータを送り続けても`0x0629`の値が一切変化しないことを確認した——リングバッファ占有量説
自体は否定されないが、その変動には`mnservice.exe`固有のフローコントロール通知が
必要である可能性が高いと判明した。詳細は
[tools/direct_usb/README.md](../direct_usb/README.md)「続報」を参照。

**新発見4: `0x0600`の状態遷移をライフサイクル全体で確認**。従来「読み書き混在で
1→2→0x1000→0x2000という遷移がある」とだけ分かっていたが、今回どの遷移がどの
ライフサイクル段階に対応するかが判明した:

| `0x0600`書き込み値 | タイミング |
|---|---|
| `0x1000` | `ChannelStart`中、Frequency書き込み直後 |
| `1` | `ChannelStart`中、変調パラメータ本体の書き込み後 |
| `2` | `SourceStart`〜実際のストリーミング中 |
| `0x2000` | `ChannelStop`（終了処理）時 |

つまり `0(待機) → 0x1000(設定中) → 1(設定完了/準備) → 2(送出中) → 0x2000(停止処理)` という
一貫したライフサイクル状態機械であるという解釈が、今回の観測でかなり裏付けられた（推測）。

これらの発見は全て実機の健全性に影響なく得られた（`Get-PnpDevice`で終始`Status=OK`を確認）。
再現用のcdbコマンド（`bu mnservice+0x87920 "r $t0 = r8; r $t1 = r9; gu; .printf \"READ
addr=0x%x -> data=0x%x\n\", $t0, poi($t1); g"`)は
[tools/native_analysis](../native_analysis)の手法の直接の拡張であり、「関数エントリで
引数を見るだけでなく`gu`でreturnまで進めて出力バッファを読む」という新しいテクニックとして
今後も再利用できる。

### 続報10 (2026-07-26): `0x1280`〜`0x1283`は`mazo::mbroadcast::mCalibration`——正式なRF較正データ読み出し機構だった

続報9で「`0x1280`〜`0x1283`は書き込みではなく読み出しされている」と判明したのを受け、
その読み出し元を特定するため、cdbで`mnservice+0x87920`（単発読み出しヘルパー）に
「`r8`（読み出しアドレス）が`0x1280`〜`0x1283`の範囲のときだけ`kb 6`でコールスタックを記録」
という条件付きブレークポイントを張った（`.if`のネストで実現）。Ghidraの静的参照解析では
このヘルパーへの直接呼び出しが1件も見つからなかった（vtable経由の間接呼び出しのため）ため、
今回はライブのコールスタックが唯一の手がかりになった。

4回とも同じ呼び出し元チェーンを通っていた: `FUN_14009c540`（既知の"adjust power"ログ
ラッパー、続報5参照）→ `FUN_14038ca20` → `FUN_14039bdb0` → `FUN_14039bf90` → 単発読み出し
ヘルパー。このチェーンをGhidraでデコンパイルしたところ、**`mazo::mbroadcast::mCalibration`**
という専用クラスが実装するRF較正データの読み出し機構であることが判明した:

```c
// FUN_14039bdb0: 0x1220を読んで(値 & 0xffffff00) != 0x78122900ならUnavailableErrorで即終了。
// つまり「コミット済み」を示すマジック値(0x781229xx)がなければ較正データは読めない。
FUN_14038cbf0(param_2, param_1, 0x1220, &local_res20, 0);
if ((*param_1 == 1) && ((local_res20 & 0xffffff00) != 0x78122900)) {
    return UnavailableError(...);
}
// mCalibrationオブジェクトを新規確保、vtableを mazo::mbroadcast::mCalibration::vftable に設定
*(undefined ***)local_res20 = mazo::mbroadcast::mCalibration::vftable;
...
FUN_14039bf90(pSVar2, &local_res20);   // オブジェクトへ実際に読み込む

// FUN_14039bf90: 0x1228/0x1229/0x1280/0x1281/0x1282/0x1283を順に読み、
// mCalibrationオブジェクトの各フィールドへ格納する
FUN_14038cbf0(..., 0x1228, ...);  object+0x60 = 生の4バイト値
FUN_14038cbf0(..., 0x1229, ..., 1);  // 読んだ4バイトを1バイトずつ分解して格納
  object+0x6c/0x6d/0x6e/0x6f = 0x1229読み取り値の各バイト
FUN_14038cbf0(..., 0x1280, ..., 1);  object+0x70 = 16bit値
FUN_14038cbf0(..., 0x1281);          object+0x72 = 16bit値
FUN_14038cbf0(..., 0x1282);          object+0x74 = 16bit値
FUN_14038cbf0(..., 0x1283);          object+0x76 = 16bit値
```

**「較正」("Calibration")という命名がベンダー自身のソースコードに残っている**ため、
これは推測ではなく事実として言える: `0x1220`/`0x1228`/`0x1229`/`0x1280`〜`0x1283`は単なる
書き込み用レジスタではなく、**ファームウェア側が保持する（恐らく工場出荷時較正済みの）
RF電力較正テーブルを読み出すための、正式な読み出し専用インターフェース**である。
実際の読み取り値（`0x1280`=`0xa`、`0x1281`=`0x88`、`0x1282`=`0x0`、`0x1283`=`0x4`)は、
この較正テーブルの中身そのものと見てよい。

**PAGainの行き先について（推測、ただし裏付けが強まった）**: この較正読み出しは
`FUN_14038ca20`内で`*(param_1+0x70) == 2`という条件でゲートされており、この`+0x70`は
RF電力書き込み関数（`FUN_14039ba70`、続報5）が最後にキャッシュする`param_3[2]`
（クライアントが送ってきた生ワイヤ値の一部、バイトオフセット16-17）と同じフィールドである。
これまで「PAGainはどのレジスタにも書き込まれず行き止まり」と結論していたが、実際には
**PAGain（およびmPSRFPowerAdjustの他のフィールド）はレジスタに直接書き込まれるのではなく、
ソフトウェア側でこの較正テーブル（`mCalibration`）と突き合わせて使われている**、と考える
方が実態に近そうだ。つまり「PAGainレジスタ」という前提そのものが誤りで、PAGainは
較正データを参照するための**ソフトウェア側のパラメータ**であり、ハードウェアの物理的な
出力を最終的に左右するのは`DACGain`（`0x1229`書き込み）だけ、という可能性が高い
（未確定だが、これまでで最も筋の通った説明）。

これも実機の健全性に影響なく得られた（`Get-PnpDevice`で終始`Status=OK`を確認）。
再現用Ghidraスクリプトは`tools/native_analysis/ghidra_scripts/XHeadFindRfCalibrationReader.java`
（間接呼び出しのため空振り、静的解析の限界を示す例として残す）と
`XHeadDecodeRfCalibrationChain.java`（cdbで得た呼び出し元アドレス群を直接デコンパイル）。

## キャプチャ手順（案）

1. Wireshark を管理者権限で起動。
2. キャプチャインターフェース一覧から `USBPcap1`（root hub、実際のポート番号は
   `Get-PnpDevice` 等で事前に確認）を選択。
3. フィルタ例: `usb.device_address == <XHEAD-USBのアドレス>`
4. キャプチャ開始 → `xhead_studio.exe` で以下の操作を行い、対応するUSBトランザクションを記録:
   - アプリ起動直後（列挙・ベンダーコマンドでの初期化）
   - チャンネル/変調パラメータの変更
   - 放送開始 (`CmdChannelStart` 相当)
   - 放送停止
   - PowerLevel変更（連続的な値なのでコマンドの差分が追いやすい）
5. `.pcapng` として `captures/usb/` に保存（Gitには含めない。解析用に手元で保持）。

## 解析の視点

- Bulk転送（映像データ本体=TS）とControl転送（設定コマンド）を分離する。
- Controlトランザクション (`bmRequestType`/`bRequest`/`wValue`/`wIndex`) の一覧を取り、
  GUIでのパラメータ変更操作とタイムスタンプを突き合わせて意味を推定する。
- `mnFirmwareUSB.cs` / `mnControlCode.cs`（デコンパイル済み, `decompiled/mnClientDotNet/mnFramework/`）
  に `Progress` / `Param` / `Firmware` という制御コード種別があり、ファームウェア書き換えも
  同じUSBチャンネル経由と推測される。ファームウェア関連のキャプチャ・改変は特に慎重に扱うこと
  （実機を壊すリスクがあるため、まずは読み取り専用の観測に留める）。
