# direct_usb

`mnservice.exe`を一切経由せず、WinUSB経由でXHEAD-USB実機に直接コントロール転送を送るツール
（`XHeadDirectUsb.exe`）。[tools/usb_capture](../usb_capture)と
[docs/protocol/modulation_capabilities.md](../../docs/protocol/modulation_capabilities.md)で
解読した「アドレス設定→データ読み書き」のレジスタバスプロトコルを、公式スタック（gRPC・
プロパティ検証層）を完全にバイパスして直接実装している。

**プロジェクトの目標である「vendor DLL・`mnservice.exe`非依存での自前実装」を実際に達成した
最初のツール**。2026-07-25、実機での読み取り・書き込み双方を確認済み（後述）。

## 使い方

```
# 事前に mnservice.exe を停止しておくこと（WinUSBインターフェースは排他所有のため）
XHeadDirectUsb.exe                              # 既定: 読み取り専用スキャン（安全）
XHeadDirectUsb.exe --write --addr 1202 --data 000737A8   # 指定レジスタへ書き込み（要注意）
XHeadDirectUsb.exe --configure                  # CmdChannelStart相当のフル設定シーケンスを再現
XHeadDirectUsb.exe --configure --freq 473000 --constellation 1 --bandwidth 6 \
    --fft 1 --coderate 3 --guardinterval 1 --timeinterleave 3 --dacgain -10
XHeadDirectUsb.exe --stream --seconds 3          # --configure相当 + バルクOUTでnull-TSを指定秒数送出
```

- 既定（引数なし）では、確定済み・未確定のレジスタアドレス一覧を1つずつ読み取るだけの
  **読み取り専用モード**で動作する。実機への影響はない。
- 書き込みには`--write --addr <16進> --data <16進>`を**両方明示**する必要がある。
  書き込み前後にそのアドレスを読み取って結果を表示する。
- `--configure`は`mnservice.exe`の`CmdChannelStart`が実際に発行するレジスタ書き込みを
  順序ごと再現し、変調器を直接駆動する（詳細は後述のマイルストーン節）。パラメータは
  `--freq`(kHz)・`--constellation`・`--bandwidth`・`--fft`・`--coderate`・
  `--guardinterval`・`--timeinterleave`・`--dacgain`で上書き可能、省略時は
  custom_senderで動作実績のある安全な既定値（QPSK/473000kHz/DACGain=-10等）を使う。

## プロトコル実装

`docs/protocol/modulation_capabilities.md`・`tools/usb_capture/README.md`で解読した内容を
そのまま実装している:

- `bRequest=0x4A`（`SET_ADDRESS`）: `wIndex`にビッグエンディアンでアドレスをセット、
  データフェーズなし
- `bRequest=0x4E`（`READ`）: 8バイト応答 = `[アドレスのエコー4B][データ4B]`（共にBE）
- `bRequest=0x4F`（`WRITE`）: 直前にセットしたアドレスへ、`wValue`+`wIndex`の4バイト領域に
  ビッグエンディアンで詰めたデータを書き込む

**重要な注意**: WINUSB_SETUP_PACKETの`Value`/`Index`フィールドを`ushort`として通常通り
マーシャリングすると、CLRは実行環境のネイティブ（リトルエンディアン）順でバイト列を
構成してしまい、実機が期待するバイト順と一致しない。本ツールでは`RawSetupPacket`構造体で
8バイトを個別の`byte`フィールドとして定義し、エンディアンを完全に手動制御することで
この問題を回避している。

## 実証結果 (2026-07-25)

`mnservice.exe`を完全に停止した状態で読み取り専用スキャンを実行し、以下を確認した:

- 全ての確定済みレジスタ（Frequency=`0x1202`、Constellation=`0x0690`、Bandwidth=`0x0684`等）が
  `mnservice.exe`経由での観測と**完全に一致する値**を返した——実装の正しさの直接的な証拠。
- 2回連続で実行しても**完全に同一の値**が返り、読み取りが安定していることを確認。
- これらの値は**`mnservice.exe`プロセスを何度再起動しても保持されている**——つまり
  ソフトウェア側の一時的な状態ではなく、**実機のファームウェア/レジスタに永続する本物の
  ハードウェア状態**である。
- 書き込みテストとして、Frequencyレジスタ(`0x1202`)へ**現在と同じ値**（473000kHz =
  `0x000737A8`）を書き戻す実質no-op書き込みを実行し、書き込み前後で値が正しく維持される
  ことを確認した。実機・USBPcap経由の観測との整合性が取れており、書き込みパスも正しく
  動作している。

### 副産物: 「休止時」と「動作中」の値の違いから得られた新しい手がかり

`mnservice.exe`が`CmdChannelStart`を実行していない、完全に静止した状態でのレジスタ値を
初めて直接観測できたことで、いくつかのレジスタが**静的な設定値ではなく、動作中だけ意味を
持つステータス/トリガー系である**らしいことが分かった:

- `0x1220`: 休止時は`0x78122900`、`CmdChannelStart`実行中の書き込みでは常に`0x78122901`
  だった（最下位1ビットだけが異なる）。**「コミット/ラッチ用のストローブビット」説
  （書き込み時に1を立てて処理をトリガーし、処理完了後にハードウェア側で自動的に0へ戻る）を
  裏付ける追加証拠**。
- `0x1290`: 休止時は`0x00000000`。動作中は`0x45585402`（"EXT"+可変ニブル）だった。
  永続的な設定ではなく、動作中のみ有効な値を持つレジスタと見られる。
- `0x0629`: 休止時は`0x000001B7`(=439)。動作中の観測では常に`0`だった。用途不明だが、
  静的な設定ではなく何らかの動的な状態（カウンタ・フラグ等）を反映している可能性が高い。
  2回連続の休止時読み取りでは同じ439が返っており、時間経過で増加するような単純な
  アップタイムカウンタではなさそう。
- `0x0600`: 休止時は`0`。動作中は`1`→`2`→`0x1000`→`0x2000`という遷移が観測されていた
  （リングバッファの状態機械か何からしい）。

## マイルストーン: `mnservice.exe`を一切経由しないRF送出に成功 (2026-07-26)

`--configure`モードを実装し、`CmdChannelStart`時に`mnservice.exe`が実際に発行するレジスタ書き込みの
**完全な順序**をcdbキャプチャ（`cdb_stdout14.log`、`cdb_stdout17.log`で相互確認）から復元して
そのまま再現できるようにした。書き込み順序:

1. `0x0602/0x0640/0x0642/0x0641/0x0601` — 未識別だが常に同じ定数値
2. `0x1202`（Frequency）
3. `0x0600=0x1000`、`0x0681/0x0682/0x0683`、`0x1202`の再送、`0x0681`の重複送信 — 未識別
4. `0x0680=5` → `0x0690`(Constellation) → `0x0684`(Bandwidth) → `0x0691`(FFT) →
   `0x0693`(CodeRate) → `0x0692`(GuardInterval) → `0x0694`(TimeInterleavce)
   — 変調パラメータ本体はこの並びでひとまとまりに送られる
5. `0x0600=1`
6. `0x1228=0` → `0x1229`(DACGain) → `0x1221=2`(固定) → `0x1290`(EXTタグ付き値) →
   **`0x1220=0x78122901`（コミット/ストローブ、最後）**
7. `0x0629=0`（複数回）

### 実機での実行結果

`mnservice.exe`を完全に停止した状態（プロセス自体が存在しない）で、custom_senderで実績のある
安全なパラメータ（Frequency=473000kHz、Constellation=1/QPSK、Bandwidth=6、FFT=1、CodeRate=3、
GuardInterval=1、TimeInterleavce=3、DACGain=-10）を使い`--configure`を実行した。

```
XHeadDirectUsb.exe --configure
```

- 全29回の書き込みがエラーなく完了、デバイスはクラッシュせず`Get-PnpDevice`でも
  `Status=OK`のまま。
- 実行直後の読み戻しで**新発見**: `0x1220`は書き込み直後こそ`...901`（LSB=1）だが、
  シーケンス完了後の読み戻しでは`...900`（LSB=0）に**自動的に戻っていた**。
  「コミット/ラッチ用ストローブビット説」（書き込みで処理をトリガーし、処理完了後に
  ハードウェア側で自動的にクリアされる）を裏付ける直接的な証拠。
- `0x1229`（DACGain）も書き込み値`0xF6F6`ではなく`0`に読み戻った。これも同様に
  「一時的な設定値バッファで、コミット処理時に消費されて0に戻る」可能性が高い
  （未確定、推測）。

### RTL-SDRによるRF出力の検証

上記`--configure`実行直後、`rtl_power`で465〜481MHzを1秒積分・2回連続スキャンし、
送出前ベースライン（`rtlsdr_baseline.csv`、[tools/rtlsdr_analysis](../rtlsdr_analysis)で
使用したものと同一）と比較した。

| 周波数 | 1回目 delta | 2回目 delta |
|---|---|---|
| 473.02MHz | +33.94dB | +33.86dB |
| 470.35MHz | +33.84dB | +33.85dB |
| 473.63MHz | +32.98dB | +32.93dB |

470〜476MHz帯（ISDB-Tの帯域幅6MHzと一致、設定周波数473MHzとも一致）に渡って明確な
プラトーが確認でき、2回のスキャンで**±0.1dB以内の再現性**があった（一過性のパルスではなく、
持続的なRF出力であることを意味する）。数値の大きさも、`tools/custom_sender`経由の公式パイプライン
テストで観測した+37〜39dBと近い水準。デバイスは検証後も`Status=OK`のまま健全だった。

**これにより、本プロジェクトの目標だった「vendor DLL・`mnservice.exe`に一切依存しない
自前実装でXHEAD-USBを実際に駆動する」ことを、レジスタ解読からRF出力の実測検証まで
含めて達成した。**

### 事実と推測の切り分け

- **事実**: レジスタバスへの直接書き込みだけで、`mnservice.exe`・gRPC・vendor DLLを
  一切経由せずにRF電力上昇が発生し、2回のスキャンで再現した。
- **事実**: このテストではバルク転送（TSストリーム）を一切送っていない
  （`--configure`はコントロール転送のみ発行する）。にもかかわらずRF出力が観測された。
- **推測（未検証）**: 出力されている信号が正しいISDB-T変調（有効なOFDMフレーム・TS）を
  含んでいるかは不明。RTL-SDRのパワースキャンは電力レベルのみの検証であり、
  ビットレベルでの復調確認はできていない（[tools/rtlsdr_analysis](../rtlsdr_analysis)の
  既知の課題と同じ）。TSストリームなしでも変調器が何らかのアイドルパターン/ヌルパケットで
  搬送波を出しているのか、あるいは以前バルク転送で送られたTSデータがスライスバッファに
  残っていて再生されているのか、現時点では区別できない。
- **推測（未検証）**: `0x1220`/`0x1229`が読み戻し時に自動的にリセットされる挙動は、
  「ストローブ書き込みで実際にハードウェアの設定ラッチが起動した」ことの状況証拠だが、
  これらのレジスタの正確な意味（単なるレジスタ実装上の癖なのか、本当に処理完了を
  示すものなのか）は依然として未確定。

## 続報: バルク転送でTSデータを流しても出力に変化なし (2026-07-26)

上記の「TSストリームなしでもRF出力が観測された」という結果を切り分けるため、`--stream`
モードを追加した。`--configure`と同じフル設定シーケンスを送った直後、標準的なMPEG-TS
null packet形式（`sync=0x47`、`PID=0x1FFF`、continuity counter付き、ペイロードは`0xFF`
埋め）で組み立てた24064バイトスライスを、バルクOUTエンドポイント（`0x01`、USBPcapで確認済み
の実アドレス）へ`WinUsb_WritePipe`で3秒間連続送信する（**注意**: ストリーミング中に
`mnservice.exe`が並行して行っている周期的な`0x4A`/`0x4E`フローコントロール通知
（[tools/usb_capture/README.md](../usb_capture/README.md)の「続報」「続報2」参照）は
まだ完全には解読できておらず、今回は**あえて実装せずバルクデータのみ**を送った）。

```
XHeadDirectUsb.exe --stream --seconds 3
```

- 3秒間で1347スライス（約32.4MB）を転送、`WinUsb_WritePipe`のエラーは一切なし。デバイスは
  終始`Status=OK`のまま健全だった。
- 直後にRTL-SDRでスキャンしたところ、**`--configure`単体（TSデータなし）の結果とほぼ完全に
  一致**した（473.02MHz: configure単体+33.94dB・+33.86dB の2回に対し、stream版は+33.83dB。
  470.35MHz も同様に+33.84dB前後で揃う）。両者の差分を全帯域で比較しても±2〜3dB程度の
  ばらつきしかなく、特定の周波数に集中したパターンもない——これは単純な測定ノイズの範囲内で、
  **TSデータの有無によるスペクトラム上の有意な変化はなかった**と言える。

### 事実と推測の切り分け（追加）

- **事実**: フローコントロール通知（`0x4A`/`0x4E`のペア）を伴わない生のバルクOUT送信では、
  32MB・3秒間のTSデータを送ってもRTL-SDRで観測可能な変化は一切なかった。
- **推測（未検証）**: 観測しているRF出力は、レジスタ設定（周波数・変調方式等）だけで
  決まる搬送波/アイドルパターンであり、バルク転送のTSデータそのものは（少なくとも
  フローコントロール通知なしでは）変調器に反映されていない可能性が高い。ただし
  これは「TSデータが原理的に無関係」ということの証明ではなく、「フローコントロール
  通知なしでは無視される」だけの可能性も残る——`0x4A`側の`wIndex`が256刻みで増える
  正確な意味（バイトオフセットかスライス番号か等）を解読し、それを伴う形で再送すれば
  結果が変わるかもしれない。現時点では未確認。

## 今後の方向性

- フローコントロール通知（`0x4A`/`0x4E`)を伴うバルク送出を実装すれば、上記の
  「TSデータが本当に無関係なのか、通知が必要なだけなのか」を切り分けられる可能性がある。
  ただし`wIndex`の正確な単位・意味の解読が前提になる、相応に手間のかかる次のステップ。
- 読み取り専用の探索はほぼやり尽くした。未識別のまま安定して読める値を持つレジスタ
  （`0x0601`/`0x0602`/`0x0640`〜`0x0642`/`0x0680`〜`0x0683`等）について、
  `mMTSChannelParam.RegionID`との相関を実際にテストしたが、レジスタバスに一切現れず
  否定された（[tools/usb_capture/README.md](../usb_capture/README.md)「続報8」）。全ての
  マーカーテストを通じてどの送信値を変えても変化しなかったことも合わせると、設定可能な
  チャンネルパラメータとは無関係な、固定のハードウェア初期化定数である可能性が高い
  （推測）。これ以上の深掘りは費用対効果が低いと判断し、現時点で棚上げ。
- **続報（2026-07-26、フルライフサイクルキャプチャで進展）**: `0x0629`は実際のストリーミング
  中に約19ms周期で継続的に読み書きされ、値も`7`〜`472`程度で絶えず変動することを確認した——
  待機時=439固定・レジスタ設定のみ(TSデータなし)=0固定・実ストリーミング中=変動、という
  3つの文脈が綺麗に符合し、**リングバッファの占有量（キュー深度）ステータス**という解釈が
  かなり有力になった（[tools/usb_capture/README.md](../usb_capture/README.md)「続報9」）。
  本ツールから`--configure`後にこの値をポーリングし続ければ、`--stream`で送ったTSデータが
  実際にバッファへ入っているかどうかの手がかりになる可能性がある——次に試す価値のある方向性。
  また、`0x0020`〜`0x0029`という第三のレジスタ帯（デバイス接続時に一度だけ読まれる識別情報
  らしきもの、続報9参照）も新たに発見しており、本ツールの読み取り専用スキャン対象に
  追加する余地がある。
- Mode（ISDB_T以外への切替）をこの直接経路で試すかどうかは、実機を壊すリスクを
  伴う判断のため、着手前に方針を相談すること。
