# direct_usb

`mnservice.exe`を一切経由せず、WinUSB経由でXHEAD-USB実機に直接コントロール転送を送るツール
（`XHeadDirectUsb.exe`）。[tools/usb_capture](../usb_capture)と
[docs/protocol/modulation_capabilities.md](../../docs/protocol/modulation_capabilities.md)で
解読した「アドレス設定→データ読み書き」のレジスタバスプロトコルを、公式スタック（gRPC・
プロパティ検証層）を完全にバイパスして直接実装している。

**プロジェクトの目標である「vendor DLL・`mnservice.exe`非依存での自前実装」を実際に達成した
最初のツール**。2026-07-25、実機での読み取り・書き込み双方を確認済み（後述）。

## 使い方

```
# 事前に mnservice.exe を停止しておくこと（WinUSBインターフェースは排他所有のため）
XHeadDirectUsb.exe                              # 既定: 読み取り専用スキャン（安全）
XHeadDirectUsb.exe --write --addr 1202 --data 000737A8   # 指定レジスタへ書き込み（要注意）
XHeadDirectUsb.exe --configure                  # CmdChannelStart相当のフル設定シーケンスを再現(既定Mode=ISDB_T)
XHeadDirectUsb.exe --configure --freq 473000 --constellation 1 --bandwidth 6 \
    --fft 1 --coderate 3 --guardinterval 1 --timeinterleave 3 --dacgain -10
XHeadDirectUsb.exe --configure --mode 0 --constellation 4 --bandwidth 6 --fft 1 \
    --coderate 3 --guardinterval 1 --dacgain -10   # 続報3: --modeでDVB_T/ATSC/J83B等に対応
XHeadDirectUsb.exe --stream --seconds 3          # --configure相当 + バルクOUTでnull-TSを指定秒数送出
XHeadDirectUsb.exe --stream --ts-file input.ts --bitrate 20000000 --seconds 30
                                                  # 188-byte TSをループし、指定ビットレートで送出
XHeadDirectUsb.exe --stop                        # 送出停止（0x0600=0x2000、RTL-SDRで停止を実測確認済み）
```

- 既定（引数なし）では、確定済み・未確定のレジスタアドレス一覧を1つずつ読み取るだけの
  **読み取り専用モード**で動作する。実機への影響はない。
- 書き込みには`--write --addr <16進> --data <16進>`を**両方明示**する必要がある。
  書き込み前後にそのアドレスを読み取って結果を表示する。
- `--configure`は`mnservice.exe`の`CmdChannelStart`が実際に発行するレジスタ書き込みを
  順序ごと再現し、変調器を直接駆動する（詳細は後述のマイルストーン節）。パラメータは
  `--freq`(kHz)・`--constellation`・`--bandwidth`・`--fft`・`--coderate`・
  `--guardinterval`・`--timeinterleave`・`--dacgain`で上書き可能、省略時は
  custom_senderで動作実績のある安全な既定値（QPSK/473000kHz/DACGain=-10等）を使う。
- `--stop`は`0x0600=0x2000`（`mnservice.exe`の`CmdChannelStop`で観測される値、続報9・15参照）
  を単体送信する。`--configure`で開始したRF送出を実際に止められることをRTL-SDRで確認済み
  （送出中+38dB前後→停止後は+7〜9dB程度のノイズフロアまで低下、2026-07-26）。
- `--stream`は既定ではnull TSを20,000,000 bit/sで送る。`--ts-file`には188バイトTSパケット
  境界から始まるファイルを指定でき、EOFで先頭へ戻る。先頭32パケットの同期バイトとファイル
  サイズを事前検証する。`--bitrate`はbit/s単位。以前の実装はWinUSBが受理する限り無制限に
  （実測約80Mbit/s）書いていたため、デバイス側リングのオーバーランという交絡因子があった。
  現実的なレートへペーシングした今回の経路で再検証する必要がある。

## プロトコル実装

`docs/protocol/modulation_capabilities.md`・`tools/usb_capture/README.md`で解読した内容を
そのまま実装している:

- `bRequest=0x4A`（`SET_ADDRESS`）: `wIndex`にビッグエンディアンでアドレスをセット、
  データフェーズなし
- `bRequest=0x4E`（`READ`）: 8バイト応答 = `[アドレスのエコー4B][データ4B]`（共にBE）
- `bRequest=0x4F`（`WRITE`）: 直前にセットしたアドレスへ、`wValue`+`wIndex`の4バイト領域に
  ビッグエンディアンで詰めたデータを書き込む

**重要な注意**: WINUSB_SETUP_PACKETの`Value`/`Index`フィールドを`ushort`として通常通り
マーシャリングすると、CLRは実行環境のネイティブ（リトルエンディアン）順でバイト列を
構成してしまい、実機が期待するバイト順と一致しない。本ツールでは`RawSetupPacket`構造体で
8バイトを個別の`byte`フィールドとして定義し、エンディアンを完全に手動制御することで
この問題を回避している。

## 実証結果 (2026-07-25)

`mnservice.exe`を完全に停止した状態で読み取り専用スキャンを実行し、以下を確認した:

- 全ての確定済みレジスタ（Frequency=`0x1202`、Constellation=`0x0690`、Bandwidth=`0x0684`等）が
  `mnservice.exe`経由での観測と**完全に一致する値**を返した——実装の正しさの直接的な証拠。
- 2回連続で実行しても**完全に同一の値**が返り、読み取りが安定していることを確認。
- これらの値は**`mnservice.exe`プロセスを何度再起動しても保持されている**——つまり
  ソフトウェア側の一時的な状態ではなく、**実機のファームウェア/レジスタに永続する本物の
  ハードウェア状態**である。
- 書き込みテストとして、Frequencyレジスタ(`0x1202`)へ**現在と同じ値**（473000kHz =
  `0x000737A8`）を書き戻す実質no-op書き込みを実行し、書き込み前後で値が正しく維持される
  ことを確認した。実機・USBPcap経由の観測との整合性が取れており、書き込みパスも正しく
  動作している。

### 副産物: 「休止時」と「動作中」の値の違いから得られた新しい手がかり

`mnservice.exe`が`CmdChannelStart`を実行していない、完全に静止した状態でのレジスタ値を
初めて直接観測できたことで、いくつかのレジスタが**静的な設定値ではなく、動作中だけ意味を
持つステータス/トリガー系である**らしいことが分かった:

- `0x1220`: 休止時は`0x78122900`、`CmdChannelStart`実行中の書き込みでは常に`0x78122901`
  だった（最下位1ビットだけが異なる）。**「コミット/ラッチ用のストローブビット」説
  （書き込み時に1を立てて処理をトリガーし、処理完了後にハードウェア側で自動的に0へ戻る）を
  裏付ける追加証拠**。
- `0x1290`: 休止時は`0x00000000`。動作中は`0x45585402`（"EXT"+可変ニブル）だった。
  永続的な設定ではなく、動作中のみ有効な値を持つレジスタと見られる。
- `0x0629`: この時点の観測では、休止時は`0x000001B7`(=439)、設定直後は常に`0`だった。
  後のフルストリーミング観測では`7`〜`472`の変動も確認している。用途は未確定だが、
  静的な設定ではなく何らかの動的な状態（カウンタ・フラグ等）を反映している可能性が高い。
  2回連続の休止時読み取りでは同じ439が返っており、時間経過で増加するような単純な
  アップタイムカウンタではなさそう。
- `0x0600`: 休止時は`0`。動作中は`1`→`2`→`0x1000`→`0x2000`という遷移が観測されていた
  （リングバッファの状態機械か何からしい）。

## マイルストーン: `mnservice.exe`を一切経由しないRF送出に成功 (2026-07-26)

`--configure`モードを実装し、`CmdChannelStart`時に`mnservice.exe`が実際に発行するレジスタ書き込みの
**完全な順序**をcdbキャプチャ（`cdb_stdout14.log`、`cdb_stdout17.log`で相互確認）から復元して
そのまま再現できるようにした。書き込み順序:

1. `0x0602/0x0640/0x0642/0x0641/0x0601` — 未識別だが常に同じ定数値
2. `0x1202`（Frequency）
3. `0x0600=0x1000`、`0x0681/0x0682/0x0683`、`0x1202`の再送、`0x0681`の重複送信 — 未識別
4. `0x0680=5` → `0x0690`(Constellation) → `0x0684`(Bandwidth) → `0x0691`(FFT) →
   `0x0693`(CodeRate) → `0x0692`(GuardInterval) → `0x0694`(TimeInterleavce)
   — 変調パラメータ本体はこの並びでひとまとまりに送られる
5. `0x0600=1`
6. `0x1228=0` → `0x1229`(DACGain) → `0x1221=2`(固定) → `0x1290`(EXTタグ付き値) →
   **`0x1220=0x78122901`（コミット/ストローブ、最後）**
7. `0x0629=0`（複数回）

### 実機での実行結果

`mnservice.exe`を完全に停止した状態（プロセス自体が存在しない）で、custom_senderで実績のある
安全なパラメータ（Frequency=473000kHz、Constellation=1/QPSK、Bandwidth=6、FFT=1、CodeRate=3、
GuardInterval=1、TimeInterleavce=3、DACGain=-10）を使い`--configure`を実行した。

```
XHeadDirectUsb.exe --configure
```

- 全29回の書き込みがエラーなく完了、デバイスはクラッシュせず`Get-PnpDevice`でも
  `Status=OK`のまま。
- 実行直後の読み戻しで**新発見**: `0x1220`は書き込み直後こそ`...901`（LSB=1）だが、
  シーケンス完了後の読み戻しでは`...900`（LSB=0）に**自動的に戻っていた**。
  「コミット/ラッチ用ストローブビット説」（書き込みで処理をトリガーし、処理完了後に
  ハードウェア側で自動的にクリアされる）を裏付ける直接的な証拠。
- `0x1229`（DACGain）も書き込み値`0xF6F6`ではなく`0`に読み戻った。これも同様に
  「一時的な設定値バッファで、コミット処理時に消費されて0に戻る」可能性が高い
  （未確定、推測）。

### RTL-SDRによるRF出力の検証

上記`--configure`実行直後、`rtl_power`で465〜481MHzを1秒積分・2回連続スキャンし、
送出前ベースライン（`rtlsdr_baseline.csv`、[tools/rtlsdr_analysis](../rtlsdr_analysis)で
使用したものと同一）と比較した。

| 周波数 | 1回目 delta | 2回目 delta |
|---|---|---|
| 473.02MHz | +33.94dB | +33.86dB |
| 470.35MHz | +33.84dB | +33.85dB |
| 473.63MHz | +32.98dB | +32.93dB |

470〜476MHz帯（ISDB-Tの帯域幅6MHzと一致、設定周波数473MHzとも一致）に渡って明確な
プラトーが確認でき、2回のスキャンで**±0.1dB以内の再現性**があった（一過性のパルスではなく、
持続的なRF出力であることを意味する）。数値の大きさも、`tools/custom_sender`経由の公式パイプライン
テストで観測した+37〜39dBと近い水準。デバイスは検証後も`Status=OK`のまま健全だった。

**これにより、本プロジェクトの目標だった「vendor DLL・`mnservice.exe`に一切依存しない
自前実装でXHEAD-USBを実際に駆動する」ことを、レジスタ解読からRF出力の実測検証まで
含めて達成した。**

### 事実と推測の切り分け

- **事実**: レジスタバスへの直接書き込みだけで、`mnservice.exe`・gRPC・vendor DLLを
  一切経由せずにRF電力上昇が発生し、2回のスキャンで再現した。
- **事実**: このテストではバルク転送（TSストリーム）を一切送っていない
  （`--configure`はコントロール転送のみ発行する）。にもかかわらずRF出力が観測された。
- **推測（未検証）**: 出力されている信号が正しいISDB-T変調（有効なOFDMフレーム・TS）を
  含んでいるかは不明。RTL-SDRのパワースキャンは電力レベルのみの検証であり、
  ビットレベルでの復調確認はできていない（[tools/rtlsdr_analysis](../rtlsdr_analysis)の
  既知の課題と同じ）。TSストリームなしでも変調器が何らかのアイドルパターン/ヌルパケットで
  搬送波を出しているのか、あるいは以前バルク転送で送られたTSデータがスライスバッファに
  残っていて再生されているのか、現時点では区別できない。
- **推測（未検証）**: `0x1220`/`0x1229`が読み戻し時に自動的にリセットされる挙動は、
  「ストローブ書き込みで実際にハードウェアの設定ラッチが起動した」ことの状況証拠だが、
  これらのレジスタの正確な意味（単なるレジスタ実装上の癖なのか、本当に処理完了を
  示すものなのか）は依然として未確定。

## 続報: バルク転送でTSデータを流しても出力に変化なし (2026-07-26)

> **後日訂正**: 以下は当時の実験記録。`0x4A`/`0x4E`を「フロー制御通知」とした解釈は、
> 後の全呼び出し元解析により「汎用レジスタ読み出し」へ訂正された。また、この試験は
> 約80Mbit/sの無制限送信であり、リングバッファのオーバーランを排除できない。
> 現在のコードは指定ビットレートでペーシングし、`0x0629`を読み取り専用で観測する。

上記の「TSストリームなしでもRF出力が観測された」という結果を切り分けるため、`--stream`
モードを追加した。`--configure`と同じフル設定シーケンスを送った直後、標準的なMPEG-TS
null packet形式（`sync=0x47`、`PID=0x1FFF`、continuity counter付き、ペイロードは`0xFF`
埋め）で組み立てた24064バイトスライスを、バルクOUTエンドポイント（`0x01`、USBPcapで確認済み
の実アドレス）へ`WinUsb_WritePipe`で3秒間連続送信する（**注意**: ストリーミング中に
`mnservice.exe`が並行して行っている周期的な`0x4A`/`0x4E`レジスタ読み出し
（当時はフロー制御通知と誤解していた）は伴わず、バルクデータのみを送った）。

```
XHeadDirectUsb.exe --stream --seconds 3
```

- 3秒間で1347スライス（約32.4MB）を転送、`WinUsb_WritePipe`のエラーは一切なし。デバイスは
  終始`Status=OK`のまま健全だった。
- 直後にRTL-SDRでスキャンしたところ、**`--configure`単体（TSデータなし）の結果とほぼ完全に
  一致**した（473.02MHz: configure単体+33.94dB・+33.86dB の2回に対し、stream版は+33.83dB。
  470.35MHz も同様に+33.84dB前後で揃う）。両者の差分を全帯域で比較しても±2〜3dB程度の
  ばらつきしかなく、特定の周波数に集中したパターンもない——これは単純な測定ノイズの範囲内で、
  **TSデータの有無によるスペクトラム上の有意な変化はなかった**と言える。

### 事実と推測の切り分け（追加）

- **事実**: 周期的な`0x4A`/`0x4E`レジスタ読み出しを伴わない生のバルクOUT送信では、
  32MB・3秒間のTSデータを送ってもRTL-SDRで観測可能な変化は一切なかった。
- **現在の評価**: RF出力が搬送波/アイドルパターンだけだった可能性は残るが、この試験は
  約80Mbit/sで送っており、想定TSレートを大幅に超えていた。「通知不足が原因」という当時の
  推測は撤回し、ビットレート制御版での再検証結果が出るまで結論保留とする。

### 続報 (2026-07-27): `0x0629`をストリーミング中に継続ポーリング——リングバッファ占有量説と矛盾する結果

[tools/usb_capture/README.md](../usb_capture/README.md)「続報9」では`0x0629`が
休止時=439固定・レジスタ設定のみ(TSデータなし)=0固定・実際の（`mnservice.exe`経由の）
ストリーミング中=7〜472で変動、という3状態を示しており、「リングバッファの占有量
（キュー深度）ステータス」という解釈が有力とされていた。この解釈が正しければ、
本ツールの旧`--stream`（生のバルクOUT無制限送信）でも、
大量のTSデータを送り続ければ`0x0629`が変動するはずである——これを実際に確かめるため、
`--stream`にバルク書き込みと`0x0629`の読み取り（制御転送）を交互に行うポーリング機能を
追加した。

```
XHeadDirectUsb.exe --stream --seconds 6
```

**結果（事実）**: 6秒間・2708スライス（約65MB、`WinUsb_WritePipe`エラーなし）を送り続けた
間、200ms間隔で計30回ポーリングした`0x0629`の値は**一度も変化せず、常に`0`のままだった**
（送信直前の`--configure`シーケンス自体が最後に`0x0629=0`を2回書き込んで終わるため、
その値がストリーミング中も一切動かなかったことになる）。

**交絡因子の検討と追試（事実）**: [tools/usb_capture/README.md](../usb_capture/README.md)
「続報9」で観測された実際の（`mnservice.exe`経由の）ストリーミングでは、`0x0629`は
**読み取りだけでなく約19ms間隔で書き込み（常に`0`）とペアで**発生していた——最初の
テストは`--configure`の最後に`0x0629=0`を2回書いたきり読み取りのみだったため、
「値が実際に変動しない」のか「書き込みという起爆動作が無いため読み取り自体が更新
されない」のかを切り分けられなかった。そこでポーリングを「`0x0629=0`書き込み→
即座に読み取り」というペアに変更し（続報9と全く同じ往復パターン）、同条件で再実行
したところ、**結果は同じく`0629`固定のままだった**（6秒間・2659スライス、
約64MBを送信、エラーなし）。これにより「書き込みトリガーの有無」という交絡因子は
否定された。

**現在から見た結論**:
- **過去の観測事実**: 無制限の生バルクOUT送信では、`0x0629=0`書き込み→
  読み取りというペアを続報9と同じパターンで送りながらでも、65MB前後のTSデータを送り
  続けて`0x0629`の値に一切変化がない。単なる読み取り専用ポーリングでも、書き込み込みの
  ポーリングでも結果は同じ。
- **訂正後の評価**: `0x4A`/`0x4E`は通知ではないため、「通知が本質的に必要」という結論は
  撤回する。無制限送信によるオーバーランと、観測対象への0書き込みという2つの交絡因子が
  残る。指定ビットレート・読み取り専用観測での再試験が必要。

## 現在の未解決事項

- 実TSを規定ビットレートで送る新しい`--stream --ts-file ... --bitrate ...`を実機で試し、
  `0x0629`が0固定から変動へ変わるか、RFスペクトルへ差が出るかを確認する。
- 実ストリーミング中に読まれる`0x2000`台のレジスタについて、アドレスと戻り値を時系列で
  採取し、リングの書き込み位置・読み取り位置との対応を特定する。
- 読み取り専用の探索はほぼやり尽くした。未識別のまま安定して読める値を持つレジスタ
  （`0x0601`/`0x0602`/`0x0640`〜`0x0642`/`0x0680`〜`0x0683`等）について、
  `mMTSChannelParam.RegionID`との相関を実際にテストしたが、レジスタバスに一切現れず
  否定された（[tools/usb_capture/README.md](../usb_capture/README.md)「続報8」）。全ての
  マーカーテストを通じてどの送信値を変えても変化しなかったことも合わせると、設定可能な
  チャンネルパラメータとは無関係な、固定のハードウェア初期化定数である可能性が高い
  （推測）。これ以上の深掘りは費用対効果が低いと判断し、現時点で棚上げ。
- **続報（2026-07-26、フルライフサイクルキャプチャで進展）**: `0x0629`は実際のストリーミング
  中に約19ms周期で継続的に読み書きされ、値も`7`〜`472`程度で絶えず変動することを確認した——
  待機時=439固定・レジスタ設定のみ(TSデータなし)=0固定・実ストリーミング中=変動、という
  3つの文脈が綺麗に符合し、**リングバッファの占有量（キュー深度）ステータス**という解釈が
  かなり有力になった（[tools/usb_capture/README.md](../usb_capture/README.md)「続報9」）。
  本ツールから`--configure`後にこの値をポーリングし続ければ、`--stream`で送ったTSデータが
  実際にバッファへ入っているかどうかの手がかりになる可能性がある——次に試す価値のある方向性。
  また、`0x0020`〜`0x0029`という第三のレジスタ帯（デバイス接続時に一度だけ読まれる識別情報
  らしきもの、続報9参照）も新たに発見しており、本ツールの読み取り専用スキャン対象に
  追加する余地がある。
- Mode切替はDVB_T/J83A/ATSC/J83B/DTMB/ISDB_T/J83Cまで実機確認済み。未確認なのは
  DVB_T2のみであり、規格上有効なパラメータと生レジスタ対応が分かるまで安全ゲートを維持する。

### 続報 (2026-07-26): 送出停止シーケンスを発見、GUIに統合

これまで本ツールには「送出停止」の確立された手順が無かった（`--configure`は起動のみの
一方通行）。`mnservice.exe`側の`CmdChannelStop`時に観測されていた`0x0600=0x2000`
（[tools/usb_capture/README.md](../usb_capture/README.md)「続報9」のライフサイクル表で
「ChannelStop/teardown」と推定していた値）を実験的に単体送信したところ、**RTL-SDRで実際に
RF出力の停止を確認できた**（+44dBの明確なプラトーから、停止コマンド送信後はノイズフロア
相当の+7〜11dBまで低下）。詳細・検証手順は
[docs/protocol/modulation_capabilities.md](../../docs/protocol/modulation_capabilities.md)
「続報15」を参照。

このロジックは`tools/custom_sender`のGUI（`DirectUsbSession.cs`）に統合済み——GUIの
「接続方式」トグルで「直接USB」を選ぶと、`mnservice.exe`を一切経由せずWinUSB直接で
変調パラメータ+RF電力設定を送出できる（対応範囲はレジスタで表現できるものに限られ、
Source添付・チャンネル/番組メタデータは非対応）。本ツール(`XHeadDirectUsb.exe`)自体にも
`--stop`を追加済み（`RunStopSequence`）——単体で送出開始・停止の両方が完結する。

### 続報2 (2026-07-26): 本ツール単体でDVB_T相当の送出にも成功——ISDB_Tとレジスタを完全共有

`docs/protocol/modulation_capabilities.md`「続報17」の詳細だが、要点だけここにも記録する。
`--configure`の`--constellation`等の引数は生のレジスタ値をそのまま渡すだけなので、
`mnservice.exe`経由のDVB_Tモードテスト（続報13）で使ったのと同じ値
（`--constellation 4`=DVB_TのQAM64生値、他は共通）を渡すだけで、コード変更なしに
DVB_T相当の設定を送出できた:

```
XHeadDirectUsb.exe --configure --constellation 4 --bandwidth 6 --fft 1 --coderate 3 \
    --guardinterval 1 --timeinterleave 3 --dacgain -10
```

RTL-SDRで473.6MHz付近に+37.7dBの明確なRF出力を実測、`--stop`で停止も確認済み。
`mnservice.exe`を一切経由しない非ISDB-Tモード送出の最初の実証例——本プロジェクトの
「mnservice.exe完全非依存の送出」（続報7・15）と「非ISDB-Tモードへの切替」（続報12・13）が
初めて同時に成り立った。ビットレベルでの規格準拠は他の全RFテストと同じく未検証。

### 続報3 (2026-07-27): `--mode`引数を追加、ATSC/J83Bも本ツール単体で送出成功

`docs/protocol/modulation_capabilities.md`「続報19」の詳細だが、要点をここにも記録する。

これまで`RunConfigureSequence`は`0x0680`を「意味不明な定数5」として常に固定送信していたが、
ATSC/J83Bの実機ネイティブレジスタ書き込みをcdbで新たに捕捉した結果、`0x0680`の書き込み値が
4モード全て（DVB_T=0/ATSC=2/J83B=3/ISDB_T=5）で`mModulationParam.Mode`のraw enum値と
完全に一致することが判明した——単なる定数ではなく、**モード選択レジスタだった可能性が高い**。
あわせて、ATSC/J83Bは`Bandwidth`/`FFT`/`CodeRate`/`GuardInterval`の各レジスタを一切
書き込まないこと（Constellationのみで完結するフィールド構造のため）、DVB_TはISDB_Tと違い
`TimeInterleavce`を書かないことも確認した。

これを受けて`--mode <値>`引数を追加し、`0x0680`を実際のMode値として送信、書き込む
フィールド集合もMode別に対応させた。実機での書き込み挙動を未検証のMode
（`J83A`=1・`DTMB`=4・`J83C`=6・`DVB_T2`=7）を指定した場合はデフォルトで拒否し、
`--force-untested-mode`を明示しない限り実行できない（特にDTMB/J83Cは`mnservice.exe`経由でも
本物のサービスハングが確認済みのため）:

```
XHeadDirectUsb.exe --configure --mode 0 --constellation 4 --bandwidth 6 --fft 1 \
    --coderate 3 --guardinterval 1 --dacgain -10                        # DVB_T
XHeadDirectUsb.exe --configure --mode 2 --constellation 0 --dacgain -10 # ATSC (8VSB固定)
XHeadDirectUsb.exe --configure --mode 3 --constellation 1 --dacgain -10 # J83B (QAM64)
```

ライブ検証: DVB_T（正しい`--mode 0`）で+37.8dB、ATSCで+38.0dB、J83Bで+35.6dBをRTL-SDRで
実測、いずれも`--stop`でノイズフロアまで低下することを確認。また、修正前の
「`0x680=5`のままDVB_TのConstellation値だけ送っていた」旧DVB_Tテスト（続報2）の結果と
新しい正しい`--mode 0`の結果を直接比較したところ、電力スペクトルの形状はノイズレベル
（差分最大1.7dB程度）でほぼ同一だった——`0x680`が物理層の変調方式を直接切り替えている
のか、`mnservice.exe`内部向けのソフトウェア的なフラグに過ぎないのかは、この粗い電力スキャン
だけでは判別できず未確定（詳細は`modulation_capabilities.md`「続報19」）。

この時点ではDVB_T/ATSC/J83Bまで対応した。その後の続報4・5でJ83A/DTMB/J83Cにも拡張し、
現在はISDB_Tを含む7モードを本ツール単体で送出できる。`tools/custom_sender`のGUIにも
続報20・23で6モード（J83Aを除く）を統合済み。

### 続報4 (2026-07-27): DTMB・J83C——`mnservice.exe`経由だとハングするモードが、本ツール単体だと成功する

`docs/protocol/modulation_capabilities.md`「続報22」の詳細だが、要点をここにも記録する。
続報13で確立した「`DTMB`/`J83C`は`mnservice.exe`をサービスごとハングさせる」という
既知の問題は、`mnservice.exe`というソフトウェア層特有の問題である可能性を検証した。

```
XHeadDirectUsb.exe --configure --mode 6 --constellation 2 --force-untested-mode --dacgain -10  # J83C
XHeadDirectUsb.exe --configure --mode 4 --constellation 2 --bandwidth 8 --coderate 2 \
    --carrier 0 --frame 1 --interleave 3 --force-untested-mode --dacgain -10                    # DTMB
```

**結果**: J83C・DTMBともに`mnservice.exe`を一切経由しない状態では**ハングせず正常に完走**、
RTL-SDRでそれぞれ+38.5dB・+38.7〜39.4dB（DTMBは2回実行して再現性確認済み）のRF出力を
実測した。DTMBは他モードと異なる独自のフィールド構成（Constellation/Bandwidth/CodeRate/
Carrier/Frame/Interleave）を持つため、`--carrier`/`--frame`/`--interleave`引数を新設し、
cdbで捕捉した実機ネイティブの書き込み順を`RunConfigureSequence`に追加した——捕捉時に
`CodeRate`と`Carrier`が同一レジスタ`0x0692`へ連続して書き込まれ、後勝ちで`Carrier`の値
のみ残るという興味深い（原因不明の）挙動も見つかった。

これにより、`--force-untested-mode`なしでMode 0/2/3/4/5/6（DVB_T/ATSC/J83B/DTMB/ISDB_T/J83C）
の6モードが`direct_usb`単体で送出可能になった——**STUDIO本体・その公式ソフトウェアスタック
（`mnservice.exe`）ではハングして実現できないモードを、独自ツールでのみ実現した**、本
プロジェクトが当初から掲げていた「STUDIOを超える」という目標の明確な達成例。J83A(1)/
DVB_T2(7)は`mnservice.exe`の**ソフトウェア検証**で拒否されていただけで実機に到達すら
していないため、依然`--force-untested-mode`が必要（実機での生レジスタ挙動が本当に
未知数のため）。

### 続報5 (2026-07-27): J83AもGhidra静的解析に基づき成功——`--force-untested-mode`不要な7モードに

`docs/protocol/modulation_capabilities.md`「続報24」の詳細だが、要点をここにも記録する。
Ghidraで`mnservice.exe`の`"modulation param invalid"`エラー元を静的解析したところ、
J83Aの拒否は実機の能力チェックではなく、**J83Aのプロパティ記述子がシンボルレート
らしき値（5000〜7999の範囲）を設定する手段を公開していないために生じるソフトウェア側の
制約**と判明した（DTMB/J83Cの「ソフトウェア層のハング」と同系統の「mnservice.exe実装の
制約であって実機の限界ではない」パターン）。

```
XHeadDirectUsb.exe --configure --mode 1 --constellation 2 --force-untested-mode --dacgain -10  # J83A
```

J83Aはレジスタレベルでは「Constellationのみ」というATSC/J83B/J83Cと同じ構造のため、
安全性を検討の上ライブ検証したところ、**2回連続でハングなく完走、RTL-SDRで
それぞれ+44.2dB・+37.0dBの明確なRF出力を実測した**（単一キャリアQAMのため
OFDMモードとはスペクトル形状が異なる狭いピーク状——J83Aの信号特性として自然）。
`--force-untested-mode`なしで使える検証済みModeがこれで7つ（DVB_T/J83A/ATSC/J83B/
DTMB/ISDB_T/J83C）になった——未検証のまま残るのはDVB_T2のみ。

DVB_T2についても同じ静的解析を行ったが、こちらは`mmodulation_param.cc`という実
ソースファイル・具体的な規格エラーメッセージ（`"PilotPattern not valid"`等）を
持つ**正真正銘のDVB-T2規格準拠パラメータ組み合わせ検証**と判明し、J83Aのような
単純な「設定手段の欠落」ではなかった。2種類の代替パラメータ組み合わせを
`tools/custom_sender --dvbt2alt`で試したが、いずれも同じ`"modulation param invalid"`
で拒否され、正しい組み合わせの特定には至らなかった（`mnservice.exe`は両回とも健全に
生存、実害なし）——引き続き未解決事項として残す。
